# 0017. Intermediate representation and where optimisation runs

- **Status:** Accepted, partly built: the IR, lowering and conversion (items 1 to 5 and 7). Items 11, 12 and 15, and specialisation, are not built and not scheduled
- **Date:** 2026-11-18
- **Related:** 0002 (closure entries that tier-up replaces), 0003 (ownership inference), 0004 (return points become frames), 0005 (run-format bytecode), 0006 (one code generator), 0008 (background compilation), 0010 (contracts, checked entry points), 0012 (distribution format, linking), 0013 (`vali build`), 0014 (positions), 0015 (the expander's tree), 0018 (library ABI versions)

## Context

Without an IR, a compiler goes from the expander's tree straight to run-format bytecode, turning loops into jumps by special-casing them and inlining calls to standard procedures, and that is all. An optimising compiler needs an intermediate representation, and that choice drives the rest: how libraries are distributed, what the linker does, what the JIT reads, and how ownership inference (ADR 0003) is expressed.

Several requirements bear on it:

- **Distributed libraries must survive their dependencies being replaced** by another version. Every optimisation that freezes something about another library into distributed code (an inlined body, a folded constant, a resolved method, a type) breaks when that library changes. The JVM's one such optimisation, `javac` inlining `static final` constants, is the cautionary tale in ADR 0012.
- **The whole program is visible when it is loaded.** HotSpot gets its best optimisations by waiting until it can see the classes actually loaded, and recording what it assumed so that a later load can invalidate them.
- **Loading must stay fast.** ADR 0012 #2 keeps conversion from the distribution format to run format a single linear pass, and tier 0 must be able to start at once.
- **Distributed code must be validated quickly**, and stay memory-safe however it was produced (ADR 0012 #9).
- **First-class continuations exist,** and any unknown call may capture one (ADR 0004 #8).
- **A typed variant is intended** (not built yet), with code specialised per type, falling back to dynamic dispatch where types are unknown.

The design overview and ADR 0004 said the compiler would convert to CPS. CPS with second-class continuations (Kennedy, *Compiling with Continuations, Continued*), A-normal form with join points (Maurer et al., *Compiling without Continuations*) and SSA are known to correspond (Kelsey; Appel): a join point is a continuation that is only jumped to, a join point's parameters are SSA block parameters, and lexical scope is dominance. They differ in how a non-tail call's return point is named, and in whether control flow is nested or a flat graph.

## Decision

### The IR

1. **The IR is A-normal form with join points: scoped SSA.**
   - Every intermediate value is bound once by `let`, and operands are variables or constants, so evaluation order is explicit.
   - `join j(p…) = …` binds a local continuation that is only jumped to and never escapes; `rec join` binds a loop. Join-point parameters play the role of φ-nodes.
   - A non-tail call is `let x = call f(a…)`, whose return point is what follows it. A tail call is `tail f(a…)`.
   - Control flow is nested: `if` tests a variable, and a name is visible only inside the scope that binds it. Dominance is lexical scope, so checking that every use is dominated by its definition is one walk.
   - **Everything compiled goes through it:** libraries, programs, `eval`, the REPL and macro transformers. They differ only in which passes run: evaluated code and REPL inputs get a cheap set (ADR 0013 #13), libraries the full one. There is no second path from the expander to bytecode. Rust procedures, from bridges and host-served libraries, are the only code that never passes through it; the IR refers to them by name.
   - In memory, nodes live in an arena and refer to each other by index, so passes run on worklists and never recurse on the program's nesting depth. A pass that wants a flat control-flow graph or a dominator tree builds one on demand.
2. **Return points become frames when the IR is converted to bytecode.** This is ADR 0004's commitment: continuations are never heap closures at run time. The IR is equivalent to CPS with second-class continuations, but no pass works on a CPS form.

   `vali-dist` holds the IR's types, its validator and a printer; `vali-compiler` lowers the expander's tree to it; `vali-bytecode` converts it. Conversion validates the IR, lays each function out with a join point's body before its handler, gives each variable a live interval (to a loop's end if it is bound outside the loop), and assigns slots by linear scan. A call's window goes above every slot live across it and every slot in use while its operands are computed, and operands and results are hinted into it, so arguments are computed in place; parallel moves fill windows and join-point parameters. A comparison that only an `if` tests becomes one branch instruction.
3. **Operations on values are primitive operations defined by the IR's specification:** `car`, `+`, `null?`, `vector-ref` and the rest of the standard procedures the compiler can open-code. They are part of the format, not bodies inlined from `(scheme base)`, so code that uses them depends on the specification and not on any library's implementation. The compiler emits one when the callee resolves to the standard binding (ADR 0015 #16).
4. **Each primitive operation has an effect set:** `pure`, `alloc`, `read`, `write`, `may-raise` and `may-capture`. An unknown call has every effect. Passes move, merge or remove operations only as their effects allow; in particular nothing that reads a box moves across a call that may capture a continuation.
5. **Procedures and closures:**
   - `fun $f(p…) [free…]` is a function, with the free variables its closure holds; `closure $f [v…]` allocates one.
   - `call direct $f(…)` calls a known function without a procedure check or a closure load.
   - `dispatch g(…)` calls a generic function, resolved at run time unless the linker resolves it (item 11).
   - An assigned variable that is captured, or live across a call that may capture a continuation, is a `box`; any other assigned variable becomes join-point parameters, as in SSA construction (ADR 0005 #4).

   Lowering boxes every assigned variable; turning the others into join-point parameters is left to the optimiser. Loops are lowered as closures; contification makes them `rec join`s (item 9). `call direct f(…)` and `tail direct f(…)` call a function with no free variables, which the validator checks, along with its arity; they become run format's `call-direct` and `tail-call-direct`, whose callee gets a closure of that function that its module's instance makes on first use and keeps. A function with free variables cannot be called directly yet: that needs its closure passed, which closure conversion will do. `dispatch` is not built: generic functions need it first. The primitive operations are the standard procedures the compiler open-codes.
6. **Ownership operations are never stored.** `dup x`, `drop x`, `let r = drop-reuse(x)` and constructors that build in a reuse token's memory (`cons@r`) exist only in the IR that conversion works on. They are inserted from liveness computed over the run-format slots, in a linear-time pass over each function, and only under strategies that count references. One extra `drop` in stored code would free an object still in use, so an untrusted artifact must have no way to say one. Distribution code carries each function's parameter conventions, owned or borrowed, only as hints from ADR 0003's ownership inference. A wrong hint costs speed, never safety, because conversion applies one convention on both sides of every call it compiles. Calls to other libraries and unknown calls always use the owned convention, so conventions are not part of a library's ABI. Conversion stays independent of strategy, because it runs in the compiler before any isolate's strategy is known, and hosts can build run-format code by hand. So an isolate that counts precisely places `move` and `drop` in each function as it converts it (`vali_bytecode::ownership`), and the run-format validator refuses both in any module it is given (ADR 0003). Not built yet: borrowed parameters, `dup` and drop-reuse.
7. **Every call and primitive that can fail carries a source position**, which conversion writes into the line table (ADR 0014 #9). An inlined call keeps the position it had in the code it came from. Positions also name the inlined copy they are in, and each function lists its copies with the calls they replaced, so backtraces show inlined frames (ADR 0014 #9).
8. **The IR's encoding is the distribution format's code** (ADR 0012). Variables are numbered implicitly as they are bound, so a binding costs no bytes; operands are variable numbers, written as small integers relative to the current binding; imports and constants are indexes into the artifact's reference and constant tables; `fun`, `join` and `if` are nested records with their lengths, so a reader can skip a function without decoding it. There is no stack encoding: the IR names every value, so a stack would save nothing.

   `vali-dist`'s `encode` and `decode` implement this. Only functions carry their length: nothing yet skips a branch, and terms follow in pre-order, so a `join` or `if` needs none to be read. Join points are numbered and named like variables. Integers are LEB128, signed ones zigzag; a primitive operation is its place in the format's list, which only grows at the end. Decoding never recurses, checks every count against the bytes left, and validates the module; encoding a decoded module gives the same bytes. Free variables and join-point parameters take no bytes, so decoding charges them to one budget for the whole module, one for each byte of its encoding plus a small allowance (the closures and jumps that supply them take a byte each, so code that is not dead stays within it), and none may exceed 65,536 in a function; a vector constant grows as its elements arrive, not by its declared length. What decoding allocates, and so what validation and conversion then work on, is bounded by the length of the input.

### Where each optimisation runs

9. **The compiler optimises each library using only that library's own code.** It needs each library to be expanded on its own, from fresh expansion-time instances and with its own numbering (ADRs 0001 #2 and #4, and 0015 #5). The expander does. What the compiler does is everything that cannot go stale when a dependency changes:
   - contification of local functions into join points, and loops as `rec join`;
   - inlining, constant folding, copy propagation and dead-code elimination within the library;
   - closure conversion: known calls become direct calls, non-escaping functions are lambda-lifted, closures stay flat;
   - turning assigned variables back into SSA where no continuation can copy them;
   - type inference within the library, for fixnum and flonum fast paths;
   - ownership inference: which parameters can be borrowed, recorded as hints (item 6).

   Distribution code contains only checked operations, and refers to other libraries only by name. It never contains another library's body, constant values, resolved methods or types.

   `vali-opt` does this in order. It first contifies: a closure its function uses only as the callee of one call, and to tie to itself, whose function calls itself only in tail position with its fixed arity, becomes a `rec join` at that call, its returns jumping to what followed a call for a value. A named `let` lowers to such a closure, so this is what makes it a loop; lowering no longer special-cases loops, and the analysis that did is gone. Evaluated code and REPL inputs get contification alone, so their loops are loops too. Every function is contified before the next step looks at any. Next it turns boxes back into values where nothing could tell: a box only unboxed and set, never captured or passed anywhere, becomes its current value, threaded through every join point in its scope as one more parameter, unless a call could show the difference. Re-entering a continuation copies the frame with the value the variable had at the capture, where a box holds the value last set, so a call keeps the box only when, after it returns, the box may be read before it is set and may also be set, and the call may capture a continuation. A call cannot when its callee is a quiet function of the module: a closure the same function made, or a global the module defines and assigns exactly once, to a closure, whose function calls only quiet functions (importers and evaluated code cannot assign it, and an error never returns to the frame that raised it). Procedures Rust implements count as unknown. Then it simplifies each function: constant folding of primitive operations on constants that cannot raise, copy propagation, `if`s on constants, removing `let`s whose values are unused and may only allocate or read, join points nothing jumps to, and a join point jumped to once from the loop it is in, whose handler takes the jump's place; then the constants no code uses are dropped. Before simplifying, calls to known procedures become direct calls. A known procedure is a global the module defines, assigned a closure of a function with no free variables in the run of the module's body that only makes closures and assigns globals, before anything that could run code or raise, and assigned nowhere else: it holds that closure whenever any of the module's code reads it, so reading it cannot fail, and simplification drops reads left unused. Only the module's own definitions are known, so nothing is assumed about another library. A direct call is quiet when the function it calls is. Each round rebuilds the function without recursing, at most four rounds. It runs on libraries, programs and transformers, not on evaluated code or REPL inputs (ADR 0013 #13); the prebuilt standard libraries are optimised when built. Setting `VALI_NO_OPT` turns it off, so the suite can check it changes nothing a program can see. Once every function has had those passes, small functions are inlined: a direct call to a function of at most 12 terms, taking exactly its required arguments, that never calls itself directly, is replaced by a copy of its body, spliced in as contification splices a loop but as a plain join point, which simplification then removes; each function takes at most 32 copies and stops taking them past 2,000 terms, and is simplified again. Direct calls go only to the module's own known procedures, so no body is ever copied out of another library (item 9, ADR 0012 #7). Each copy is recorded with the inlined procedure's name and the position of the call it replaced, and its positions name the copy, so backtraces still show its frame (ADR 0014 #9). The bounds are a first guess, left open below. Closure conversion, type and ownership inference are not built.
10. **Conversion to run format stays linear-time** (ADR 0012 #2): validating the IR, liveness for slot allocation, instruction selection, positions. Ownership operations are placed as each function converts instead (item 6). **A library's functions convert on their first call.** Loading decodes and validates the IR, builds the constant pool, variables, sources and exports, and converts the module's body, which runs at once; every other function stands as a descriptor with its name, arity and free-variable count and no code. Its first call checks the arity, converts the function, checks the result with the run-format validator against the module's tables, places its ownership operations under precise counting, charges the memory to the heap and calls it again, now as bytecode, so a function that has run costs nothing more and the dispatch loop's fast path is unchanged. A function never called is never converted, and neither is it validated: its IR was, which makes conversion fail only on a converter bug, and that error is raised at the call, naming the function. A debugger sees a function not called yet with no frame size and no line table, since only functions with frames are shown. Modules that `eval` and the REPL load, and ones built by hand, convert whole; so does a library when a build or a test asks for it (`VALI_EAGER`). Liveness is computed in two passes over each function, using SSA liveness for reducible control flow (Boissinot et al.); loops are explicit `rec join`s, so control flow is always reducible. Every pass is linear in the function or module, up to a logarithm: the constant pool and the source table are hashed, the loops a use is inside are kept on a stack as the uses are walked in order, parallel moves are ordered with a heap, and slots come from an ordered set of the free ones, with the highest live slot and the highest slot under a call's window found from ordered sets and range maxima. Conversion adds one constant of its own, the unspecified value, first, so a module has at most 65,535 distinct constants, or 65,536 with that one among them.
11. **The linker optimises across libraries when the program is loaded** (not built, not scheduled), with the versions of every library actually present:
    - inlining other libraries' procedures, and folding their constants;
    - resolving `dispatch` sites to direct calls where the types are known and the generic function's rules guarantee no later method can change the answer; other sites stay dynamic, optionally with an inline cache seeded by the linker;
    - instantiating specialisations of generic typed code, by converting the IR again with concrete types substituted. Each copy is linear to produce, copies are cached by function and type arguments, and their number is bounded, falling back to the shared version past the bound;
    - choosing a contracted export's unchecked entry point where the contract is proven at the call site (ADR 0010 #4).

    The link-time optimiser runs on a background thread. Tier 0 starts at once on each library's own converted code, and each optimised function replaces its entry when ready, as tier-up does (ADRs 0002 and 0008). Its results are cached under the hashes of exactly the libraries they relied on, so replacing a library makes those entries miss and they are linked again against the new version. A host can turn link-time optimisation off, leaving each library's own optimised code.
12. **Every link-time decision is proven,** never speculative (not built, with item 11). A library loaded later (dynamically, or through `eval`) may invalidate one, for example by adding a method to a generic function a site was resolved for. Each optimised function records what it relied on, as HotSpot records its dependencies; invalidating it puts its entry back to the library's own code and relinks it in the background. Frames already running in the old code finish there, and calls made after the invalidation see the new code. Invalidated code stays alive while any frame or continuation refers to it, since re-entering a continuation can return into it.
13. **The distribution format's validator is the security boundary.** Untrusted code arrives as source or as distribution artifacts. Run-format bytecode is produced only by Vali's own converter and linker, from validated IR and facts they derived themselves, and is never stored, so no copy of validated code sits outside the boundary to be changed. Loading a run-format module directly is not an entry point for untrusted input. Run format is still validated as it is converted, a library's functions each on its first call, and keeps every memory-safety check (ADR 0005 #7), as defence in depth; only native code removes checks. The distribution format's validator is what gets fuzzed. It rejects a function that declares more variables or join points than it binds, before allocating for the count, and two globals with one name and link, which would be one cell once linked. These size limits are separate from the structural checks (`validate_limits` and `validate_structure`): a module over them is not one the optimiser got wrong, so the optimiser asserts only structure, and the compiler reports a module over a limit, a library's or a program's, as a compile error when it converts it. It refuses what run format cannot hold, so that a module that validates always converts and a conversion failure can only be a converter bug: more than 65,535 constants (conversion adds one) or 65,536 globals or sources, more than 65,535 free variables or call arguments, a `set-free` index above 65,535, a function whose frame might need more than 65,535 slots, and one whose code might take more than 2^23 - 1 words, the span of a jump. Slots and code size depend on register allocation and instruction selection, so the validator checks bounds worked out from the IR alone, which the converter is guaranteed to stay under: first-fit allocation never needs a slot above the most variables live at once (counted by intervals no shorter than the converter's, in its order of terms, with the loop rule), the converter accepts hinted placements of call operands only up to that count plus the parameters, 16 operands and 8, and otherwise falls back to unhinted allocation, and a call's window and the scratch slots add at most the most operands any term has and 8 more, so a call's operands count once and a call with tens of thousands of arguments converts, within a few dozen arguments of what a frame holds; a term takes at most 4 words for each operand and 10 of its own. The bounds are conservative, but a function with many variables is refused only if they are live together. A debug build asserts that conversion stays under them. The optimiser numbers each function's variables and join points without gaps, as decoding does, so what it produces passes.


    **A check may be removed only on facts the validator enforces, or that are soundly derived from them.** Native code, and any pass that wants to drop a check, may rely on a property of the IR only if every module that passes the validator has it. A property that holds of what Vali's own compiler emits, but that a crafted artifact can break, is not a fact. The first facts, for a variable `c` bound by `let c = closure g(…)`:
    - every `set-free c i c`, a self-tie, is an ancestor in the term tree of every other use of `c`: calls, arguments, returns, free operands of other closures, and `set-free` operands. Nothing can mention `c` before it is tied, so nothing can call it early, even after it escapes. A tie in a join's body does not count for a use in its handler;
    - `set-free` names only a variable bound by a `closure` `let` in the same function, so every write to a closure's slots is visible where the closure is made;
    - no other `set-free c i _` writes a self-tied index.

    A later tier may therefore treat a self-tied slot of the closure value `c` as `c` itself, and call it directly with no procedure or tag check. This is a fact about `c`, not about `g`'s code, which every closure of `g` shares: `g`'s code may assume that slot `i` holds its own closure only if every `closure g` in the module is self-tied at `i`, which follows soundly from these rules and must be checked, not assumed from one closure. Other ties stay dynamic: `(letrec* ((f (lambda () (g))) (x (if flag (f) 0)) (g …)) …)` calls `f` before it is patched with `g`, which no static rule can reject without rejecting valid programs. An analysis must treat the type of such a slot as "placeholder or patched value", and native code must check what it reads from one, unless it proves the order.

    The validator checks the rules in one iterative walk, using each term's preorder index and subtree size for the ancestor test. `letrec` lowers a closure's self-tie before patching earlier closures with it. Contification still declines a closure whose ties do not come before its call, with a debug assertion beside it, so a pass that broke the rule would cost an optimisation and not change what a call does.
14. **The JIT reads run-format bytecode** (ADRs 0005 and 0006), including the link-optimised code. It rebuilds SSA for each function as it translates it to Cranelift (Braun et al.; Cranelift's frontend does this with `use_var` and `def_var`), which is enough for local work such as keeping flonums unboxed (ADR 0002). Facts that took analysis across functions reach it as instructions: direct calls, resolved dispatch, unchecked entry points, and the ownership operations of the code an isolate rewrote as it loaded it. A side table of further facts in run format is added only when a JIT optimisation needs one that no instruction expresses.
15. **`vali build` runs the optimiser over the whole program** (not built, not scheduled), from distribution artifacts (ADR 0013 #2): every library is fixed, so it may seal generic functions and resolve every dispatch site the types allow, then converts to run format and hands it to the shared code generator. It is publishing an application, as `dotnet publish` with ahead-of-time compilation is, not a step in ordinary development.
16. **The optimiser lives in its own crate, `vali-opt`,** used by the compiler for each library and by the loading path for the linker. The IR's types and encoding live in `vali-dist`, since they are the distribution format's code. A host that turns link-time optimisation off, and a standalone executable without `eval`, need not link `vali-opt`'s link-time half.

## Consequences

- Replacing a library never invalidates code distributed by others, beyond the macros they expanded (ADR 0012 #6): everything else about a dependency is used only at link time, and cached against that dependency's hash.
- Untrusted artifacts can claim nothing that weakens safety: distribution code holds only checked operations and no ownership operations, and the linker introduces unchecked entry points and specialised code only from facts it established itself.
- With link-time optimisation off, code is still better than the baseline compiler's: each library's own code is optimised, and primitive operations are still open-coded.
- The first run of a new combination of libraries runs on per-library code while link-time optimisation runs in the background; later runs read the optimised code from the cache.
- Embedding hosts that compile source carry the optimiser. It is small beside the expander they carry already, and can be left out.
- The run format gains instructions: direct calls, dispatch sites with a link slot each, and `dup`, `drop`, `drop-reuse` and reuse constructors (ADR 0005). Dispatch sites' slots live in a per-module table, so linking fills tables and never rewrites code (ADR 0005 #10).
- The IR's specification, including every primitive operation and its effect set, is part of the distribution format's specification, and has the same compatibility promise.
- There is one path from the expander to run format, through the IR, and no separate baseline code generator.
- Deoptimisation is not needed, because nothing is speculative. Speculation in the JIT would bring it back.

## Alternatives considered

- **A CPS graph of labelled continuations** ("CPS soup", as in Guile): every return point is a label, and contification is a renaming. It is equivalent for passes, but harder to specify as a stable format, inlined bodies need relabelling when spliced, and validating a flat graph needs a dominator computation where a scoped tree needs a walk.
- **Nested CPS terms** (Kennedy's `letcont` and `letval`): close to the paper, but every rewrite rebuilds the tree, and passes recurse on nesting depth.
- **Flat SSA basic blocks** (as in Cranelift or LLVM): close to the code generator, but validating them needs dominators, and the format loses the structure that keeps loading linear.
- **Optimising across libraries before distributing,** with inlining by consent: every cross-library fact is frozen into artifacts and checked on load, so replacing a library breaks or refuses its importers, and library authors must decide what to mark inlinable.
- **Speculative optimisation with deoptimisation,** as HotSpot does: more speed on hot code, but it needs profiling and a way to rebuild tier-0 frames from optimised ones. It remains possible in the JIT later.
- **Giving the JIT the IR as a second input:** richer facts, but two inputs to keep consistent, and warm runs would have to keep the IR reachable.

## Left open

- **Generic functions and the typed variant:** the rule that makes resolving a dispatch site final (an orphan rule, sealing declarations or both), whether the typed variant's types are sound inside typed code, and how its annotations are checked on load. Item 11 is built to accept either.
- The exact set of primitive operations and their effect sets, which belongs in the distribution format's specification rather than an ADR.
- The order of passes and their budgets, including the inlining heuristics and the bound on specialisations.
- Speculation and deoptimisation in the JIT.
- Whether the compiler also specialises its own generic code ahead of time, for types it knows will be used.
