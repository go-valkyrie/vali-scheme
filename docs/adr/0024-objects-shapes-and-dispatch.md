# 0024. Objects, shapes and dispatch

- **Status:** Proposed
- **Date:** 2026-11-19
- **Related:** 0002 (values, headers, records, tier-up entries), 0003 (memory strategies), 0004 (continuations), 0005 (run-format bytecode, tables), 0008 (isolates, one thread at a time), 0009 (capabilities), 0012 (distribution format, the validator), 0016 (Rust objects), 0017 (the IR; #5 `dispatch`, #11 link-time resolution, #12 invalidation), 0020 (constants), 0023 (resource limits)

## Context

Vali's only user-defined data type is the record: a header, a type descriptor and a fixed list of fields, read and written by `%record-ref` and `%record-set!` after a check against the descriptor (`crates/vali-runtime/src/records.rs`; `define-record-type` in `(scheme base)`). ADR 0017 #5 names a generic `dispatch g(…)` instruction and #11 lets the linker resolve it, but neither says what a generic function is, what it dispatches on, or what an object is beyond a record.

The owner wants four things from this, in this order:

1. **CLOS, with the full metaobject protocol:** classes, generic functions with multiple dispatch, `eql` specialisers, method combination, class redefinition, and AMOP's protocol for user metaclasses, slot-definition objects, `compute-applicable-methods`, `compute-effective-method` and customisable dispatch. The MOP lives in a Scheme library; the VM's job is to keep it fast.
2. **ES6 objects as a bonus:** prototypes, property descriptors, `Symbol` keys, arrays with holes, `#private` names, and optionally `Proxy`.
3. **The door open for other front ends** (Python, Ruby, Lua, Smalltalk-likes, Dylan, Julia-like DSLs) that an embedder might compile to Vali's IR to get its sandbox, limits and validation (ADRs 0009, 0012, 0023). Their object models differ, but the VM needs the same few mechanisms under each.
4. **Hot module replacement:** reloading a library into a running isolate while its classes still have live instances and its code is still on continuations. It gets a record of its own (Left open); this one makes sure shapes and caches do not stand in its way, which is why shapes are collectable (item 1).

A bytecode VM with no object support cannot make any of these fast, and cannot make them safe without checks that cost what the fast path saves. Every fast dynamic-language VM converged on the same substrate, and the substrate is small enough to be language-neutral:

- **Shapes** (V8's maps, Self's maps, PyPy's maps, Truffle's shapes): an immutable description of an object's layout, shared by every object built the same way, so that "which slot holds `x`" is a property of a pointer comparison. V8 puts the shape in the first word of every object and describes properties in a descriptor array shared along a transition chain; objects with the same properties added in the same order end up with the same map ([V8, hidden classes](https://v8.dev/docs/hidden-classes)). PyPy's maps are "immutable, immortal and reused as much as possible"; an instance is a map pointer plus a storage array, and a million three-field instances took about 40 MiB with maps against 177 MiB without them (32-bit, [PyPy, 2010](https://pypy.org/posts/2010/11/efficiently-implementing-python-objects-3838329944323946932.html)). Truffle's object model is the same idea with typed storage locations: a shape maps property names to locations in a fixed number of in-object fields plus an extension array ([Wöß et al., PPPJ 2014](https://chrisseaton.com/rubytruffle/pppj14-om/pppj14-om.pdf); [Truffle's Dynamic Object Model](https://www.graalvm.org/dev/graalvm-as-a-platform/language-implementation-framework/DynamicObjectModel/)).
- **Inline caches** at access and call sites, which remember the shapes seen there and what they resolved to. V8 keeps up to about four maps at a site (polymorphic) and falls back to a global stub cache keyed by map and name once a site goes megamorphic ([V8, hidden classes and ICs](https://chromium.googlesource.com/v8/v8/+/HEAD/docs/runtime/hidden-classes-and-ics.md)).
- **Dispatch caches** for generic functions. GOOPS memoises the method chosen per tuple of argument classes on the generic itself, with a short linear search for small caches and a hashed search for larger ones, and drops the cache when a method is added or a MOP method is redefined ([Wingo, 2008](https://wingolog.org/archives/2008/10/17/dispatch-strategies-in-dynamic-languages)). PCL, the CLOS implementation under SBCL, gives each class a *wrapper* with a stored value that generic functions' small memoisation tables are indexed by; redefining a class zeroes the wrapper's value, so instances of the old class miss the table on their next dispatch and normal dispatch pays nothing for the check ([Kiczales and Rodriguez, 1990](https://dl.acm.org/doi/10.1145/91556.91600); [summary](http://axisofeval.blogspot.com/2010/07/efficient-method-dispatch-in-pcl.html)). Julia keeps a method table per generic function, caches by argument types, and makes redefinition safe with a *world age*: a global counter bumped by every method or binding change, with each task seeing the world it started in ([Julia manual, world age](https://docs.julialang.org/en/v1/manual/worldage/)).

Constraints that come from Vali's other records:

- **The distribution format's validator is the security boundary** (ADR 0012 #9, 0017 #13). Distribution code holds only checked operations. Whatever objects add must be checkable without knowing any shape, and nothing a crafted artifact says may weaken memory safety.
- **Run-format bytecode is private and executes directly.** Loading fills in per-module tables; the one rewrite at load is the ownership pass of a counting strategy (ADR 0003), and nothing patches code to cache. Dispatch sites already have a slot in a table (ADR 0005 #5). This is where caches can live.
- **Nothing is speculative** (ADR 0017 #12, consequences). A cache that falls back to the full lookup on a miss is not speculation: there is no deoptimisation. A JIT that embeds a cache's answer must record what it relied on and be invalidated like any link-time decision.
- **One thread at a time uses an isolate's heap** (ADR 0008), and continuations copy frames (ADR 0004 #8). Both make several of the problems below easier than in a multi-threaded VM, and the second adds one that is easy to forget: a frame may resume after the world has changed.
- **Five memory-strategy variants are built** (ADR 0003): no collection, and deferred and precise counting, each with headered or side-counted pairs. An object design must be correct under all of them, and must not put a barrier or a count where one is not needed.
- **Limits apply to what hostile code can grow** (ADR 0023). A shape table and a property-key table are such things.

ES6's other requirements are not objects: UTF-16 string semantics, IEEE doubles with int32 truncation, Promises and async functions, `WeakMap` and `WeakRef` (ephemerons, #37), `RegExp` (#36), `eval` and Proxy. They belong to *primitive sets* and other records, as the notes on other front ends say. This one only has to leave them room: it keeps the object substrate free of anything that would stop an ES runtime from supplying them, and says where each meets it (below).

## Options

**A. A small language-neutral substrate in the VM and IR (recommended).** Shapes with transitions; allocation by shape; guarded slot and element access; `get`/`set` by key with inline caches that exist only in run format; `dispatch` over specialisers with a per-argument-tuple cache; a miss hook. CLOS and ES6 are libraries over it, and records become its simplest users. Costs: new primitive operations, shapes and caches in the runtime, about as much new run-format surface as `dispatch` already needs, and a hook protocol that has to be right once. Buys: one mechanism for records, CLOS instances, ES objects and bridged Rust objects; fast paths that are a tag test, a shape compare and a load; invalidation in one place.

**B. Dispatch keyed on shapes only.** Single dispatch on the receiver's shape, as V8, Truffle and Smalltalk-style VMs do, and nothing else. Simpler cache (a site's entry is `shape → resolution`) and enough for ES and for Ruby or Python method calls. It fails the requirement that motivated the design: CLOS dispatches on all required arguments, with `eql` specialisers that depend on a *value*, and Python's binary-operator protocol tries one operand's method and then the other's (`a.__add__(b)`, then `b.__radd__(a)`), so the useful key is both classes. A library would rebuild multiple dispatch over a single-dispatch core, with its own caches in Scheme hash tables the VM cannot see, giving up the inline cache for exactly the calls that need it. Cheaper to start, more expensive to finish.

**C. No VM support: objects are records plus hash tables in Scheme.** An object is a record holding a class and a hash table (or alist) of slots; a generic function is a closure over a Scheme-side cache. GOOPS and Tiny CLOS are written this way, over a host with some VM help. Costs nothing in the VM and has no new safety surface, and `dispatch` stays unbuilt. But every property access is a hash lookup on a table the object carries: PyPy's figures above are the size of that cost for a dict-backed object, and a Scheme-level cache cannot be an inline cache, because only the VM knows when a site sees a shape. It would serve CLOS acceptably and every other language poorly, so the third goal would be abandoned in effect. Hash tables (#30) are needed for the dictionary fallback in A anyway.

**D. Adopt a Truffle-like object model wholesale.** Shapes plus typed storage locations (unboxed `long` and `double` locations, generalised to `Object` when a different type is stored, which changes the shape), property flags, extension arrays, and access nodes that cache per shape. The shapes, in-object slots plus an extension array, and per-site caching come over directly and are in A. The typed locations do not: they pay off when a partial evaluator can fold the shape check and the unboxed access across a whole call tree, and in Vali fixnums are already immediate (ADR 0002) and flonums boxed, so the gain is flonum fields, which belong to the planned typed IR (#33) and its unboxed fields. A copies Truffle's shape model and leaves its framework behind.

**E. Statically laid-out classes** (JVM and Kotlin style: a class fixes its fields and a vtable index per method, so a call is a load and an indirect call). Fastest for statically typed languages, but it needs the typed IR and the closed world that link-time resolution gives (ADR 0017 #11, #15). A can reach the same code when the linker proves a site monomorphic. Recorded as out of scope.

Three sub-choices inside A each have their own options, set out where they arise: what happens to an object with too many or too dynamic properties (transition tree against dictionary mode, item 3), how caches stay correct when classes and methods change (eager dependents against a Julia-style world counter, item 12), and who may add methods to a generic whose calls the linker resolves (item 16).

## Recommendation

Option A, built in slices (item 19), with these parts.

### Objects and shapes

1. **A shape is an immutable description of a layout, and a heap object that can be collected.** It is a first-class value of its own type code (`Shape`), made by checked primitives. It holds: the shape's *class value* (an opaque Scheme value, set at the root and inherited by every descendant; set once more after creation if the library needs it, for the metacircular start-up of a MOP); the properties in order, each a key, a slot index and a flags byte; the slot count; and its transitions, a small map from `(key, flags)` to the child shape. A shape is identified by identity, so a shape check is one comparison.

   **Lifetime.** Shapes are designed as ordinary heap objects. An object's shape word is a *counted* reference, changed once when the object is allocated and once by `become-shape` or a transition (`add!`), never on a read, and a slot read or write never touches it. A shape refers to its parent strongly, so a live shape keeps its ancestors; a parent's edge to a child is *weak*, so an unused branch of the tree can go. Inline caches never keep a shape alive: each shape keeps a list of the sites that cache it (the eager dependents of item 12), and freeing a shape clears those entries first. A root and its class value refer to each other, so they form cycles, which the strategy's cycle collector handles like any other. A shape therefore dies when no object has it and no live shape descends from it, which is what a program that makes a root per object in a loop, and a hot-reloaded module's old classes once their instances are gone, both need. Weak edges need weak references (ADR 0003's contract; #37), so collectability is its own slice (item 19). **Not built yet:** until then shapes are immortal behind the same API, by the rule ADR 0020 gives constants: a shape's count is stuck at its maximum, nothing counts or frees it, and trial deletion treats it as a leaf, so the objects' shape word is a counted store already and moving to collectable shapes changes the shape's header and the tree's edges, not objects or code. Shapes are bounded by `max_shapes` in ADR 0023's configuration type. At the bound `shape-root` raises ADR 0023's catchable limit error, as the symbol and syntax caps do, and `shape-extend` sends the object to dictionary mode (item 3). Until collectable shapes land this also bites programs that make a root per object (Ruby singleton classes, `setPrototypeOf`): they hit the limit and can catch it, where a program that only grows properties degrades quietly.
2. **The class value is the root's identity.** Two objects have the same shape only if they share a root and the same properties added in the same order. The root's class value is what the other systems store in different places: PyPy puts the class at the end of the map chain, V8 puts the prototype in the map, PCL's wrapper points to the class. Here it is the CLOS class, the ES prototype, the Python type, the Ruby singleton or class, or a record type descriptor, and the VM interprets it only as an identity to key dispatch on, and as where the miss hook (item 7) lives. It is *the library's* choice what it means.
3. **Transition tree for ordinary growth, dictionary mode past a bound.** `shape-extend shape key flags` returns the child for that key, creating it on first use. A tree gives the sharing that makes caches work and costs one Rust-side node per distinct layout; it degrades when objects use many keys, delete keys other than the last added, or use keys chosen by data (a hash map used as an object), since every distinct path then makes new shapes. Past `max_shape_properties` (first guess 128), on a delete of anything but the last-added property, or when `shape-extend` would pass `max_shapes`, an object switches to **dictionary mode**: its shape word becomes the *dictionary shape of its root* (one per root, shared, flagged `dict`), and its `props` word points to an open-addressed table in the heap holding key, flags and value. V8 uses the same two modes; PyPy moves an instance's data into a dictionary when a non-string key arrives, and judges the cost acceptable because it is rare ([PyPy, 2010](https://pypy.org/posts/2010/11/efficiently-implementing-python-objects-3838329944323946932.html)). Taking the table into the heap, and a shared shape for every dictionary object of one class, means a dictionary object adds no shape to the table and its properties die with it: the per-object property table a Rust-side "unique shape" would need could never be freed, which is the leak that would make this a denial-of-service lever. Inline caches never cache named lookups on a dictionary shape; they take the table lookup each time. Moving between modes is one-way.
4. **Layouts.** Two, chosen at allocation and recorded in the header's runtime data:
   - **Fixed:** header, shape, then the slots. A record with three fields is 40 bytes, exactly as now (the descriptor word becomes the shape word). The shape must have `fixed` set at its root, so `add` and `delete` raise. This is the layout records use.
   - **Open:** header, shape, `props`, `elements`, then a number of inline slots. `props` points to the heap vector that holds slots past the inline ones (or the dictionary table, in dictionary mode) or is empty; `elements` points to the element store (item 6) or is empty. Four words of fixed overhead, plus eight bytes a slot. The inline count comes from the allocation site's size hint, so an object does not start by moving its first properties out, which V8 solves with slack tracking and Truffle with `@DynamicField`s. An ES object with four properties is 64 bytes plus no extra allocation. Both layouts keep their slot count in the header's 24 bits of runtime data, as a record keeps its field count now (ADR 0002 #7), so the strategy can walk an object's pointers without the shape.
5. **Per-object behaviour is the object's own shape.** `become-shape o shape'` changes an object's shape word. It is checked: `shape'` must have a slot count no larger than the object's capacity (inline plus `props`), and new slots read as the unspecified value until written. This is the one operation that lets a library implement Ruby singleton classes (`def obj.m`, which move the object to a fresh root whose class is a singleton), ES `Object.setPrototypeOf` (move to the tree for the new prototype, re-adding the properties in order), CLOS `change-class` and class redefinition (below), and shape migration generally. Each new root costs one shape and its transitions, a few tens of bytes, which the library keeps cheap by making roots lazily and sharing them (an ES runtime caches "the root for objects whose prototype is `p`" on `p`). While shapes are immortal this is a leak for programs that make a fresh root per object in a loop; item 1's collectable shapes remedy it.
6. **Elements: indexed storage beside named slots.** The `elements` word points to an element store whose header data holds a *kind*: **packed** (a vector, with a length and capacity), **holey** (the same, with a distinguished internal `hole` marker, ADR 0002's immediates) and **sparse** (an open-addressed table from fixnum index to value). Kinds only move one way, packed to holey to sparse, as V8's elements kinds do ([V8, elements kinds](https://v8.dev/blog/elements-kinds)); V8 also keeps unboxed SMI and double kinds, which are out of scope here (they need unboxed fields). An index far past the capacity moves the store to sparse instead of allocating. This gives ES arrays (holes, `length` as the store's length), Lua tables (the array part is elements, the hash part is props in dictionary mode), Python lists and Ruby arrays a representation, with the bounds check in the VM.

### IR operations and caches

7. **The operations are primitive operations in a named set, `(vali object)`,** with effect sets as in ADR 0017 #4. They are part of the IR's specification like any primitive, and a front end that does not use objects never mentions them.

   | Operation | Effects | What it does |
   |---|---|---|
   | `shape-root class flags`, `shape-extend shape key flags`, `shape-of o`, `shape-class shape`, `shape-slots shape` | `alloc`, `pure` | Make and read shapes. A key is a symbol (item 9) |
   | `alloc-object shape hint v…` | `alloc` | An object of that shape, with the given slots; fixed or open by the root's `fixed` flag |
   | `slot-ref o shape i`, `slot-set! o shape i v` | `read`, `write`, `may-raise` | **Guarded by shape.** Raises unless `o` is an object, `o`'s shape is `shape`, and `i < shape`'s slot count; a read-only slot refuses `slot-set!`. This is a record's accessor |
   | `get o key`, `get-in o key scope`, `set! o key v`, `has? o key`, `add! o key flags v`, `delete! o key` | `read`/`write`, `may-raise`, `may-capture` | Lookup by key. The slow path searches the shape (or the dictionary table), then runs the miss hook (item 8). Each is a cached site (below) |
   | `elt-ref o i`, `elt-set! o i v`, `elt-length o`, `elt-resize o n` | `read`/`write`, `may-raise` | Bounds-checked element access. A read past the end or at a hole returns the `hole` marker and lets the library decide (an ES prototype walk, a Python `IndexError`) |
   | `become-shape o shape` | `write`, `may-raise` | Item 5 |
   | `dispatch g(args…)` | every effect | Item 9 and 10; ADR 0017 #5 |

   Two property flags are interpreted by the VM: `readonly` (writes raise) and `hooked` (a read or write of this property calls the class's access hook with the object, key and value, which is how ES accessor properties and Python descriptors and `__getattr__` on a known name are expressed). All other flag bits belong to the library: ES's enumerable and configurable bits, for example. The VM never needs the meaning of a flag it does not interpret, so languages with other property attributes need no VM change.
8. **The miss hook.** When `get o key` finds neither a slot nor an element, or finds a `hooked` property, the VM calls the **hook of the shape's class value** with `(o key scope)`. A class value that is a record or object with a procedure in a known place supplies it; with none, `get` raises. This is `__getattr__`, `method_missing`, `doesNotUnderstand:`, an ES prototype-chain walk and a Proxy trap, all as one mechanism. A hook returns either a value or a **resolution**, which the site may cache: `(slot-of o' i)`, `(constant v)` or `(call f)`, plus a **validity cell** (a heap cell the library clears when what the answer depended on changes: a prototype's own properties, its prototype link). A cached resolution is guarded twice, so that **no library mistake can make a hit unsafe**. A `(slot-of o' i)` entry stores the holder `o'` *and the holder's shape*, and a hit compares the receiver's shape, then `o'`'s current shape against the stored one (as V8 checks the holder's map), then the validity cell, then reads slot `i` of `o'`. The shape compare is what makes the read in bounds: `i` was checked against that shape's slot count when the entry was filled, and an object whose shape is unchanged has the slots it had. A library that fails to clear a cell, or an `o'` that has since moved to dictionary mode or been given another shape, therefore gives either a miss or a stale but in-bounds value, never a read outside the object. `(constant v)` and `(call f)` entries read no object memory. A hit still skips the chain walk; a plain value return is not cached. **A `hooked` property's value is never cached**: its read or write calls the hook every time, and a site caches only *which* hook (the resolution), so a getter may return anything. A hook may also return a cacheable `(slot-of o' i)` resolution guarded by validity cells, which is how an accessor that merely forwards to a plain slot becomes as fast as one. **Misses are cached**: a site remembers `(shape, key) → absent, hook`, so the negative search is skipped even when the hook must run. This is what makes ES property reads that find the property on a prototype, and Ruby method calls that find the method on a superclass, as fast as a shape check and a cell check, instead of a search per level. Exotic objects (a Proxy) have a root flagged `exotic`: every operation goes to the hook and nothing is cached through it, so they cost nothing to anything else.
9. **Dispatch has a specialiser per argument position and a key per specialiser.** A generic function is an *applicable object* (the applicable flag of ADR 0002 #3, on its root): a record-like object with hidden fields for its dispatch arity `k`, the specialiser kinds used at each position, the cache and the **discriminator**, a Scheme procedure the library installs. `(g a b)` and `dispatch g(a, b)` run the same code. For each of the first `k` arguments the VM computes a *cache key*:
   - **class specialiser:** the argument's class value (a shape's root class for an object; a table of built-in classes for fixnums, pairs, strings, flonums and the other tagged values), which for an object is already on its shape;
   - **`eql` specialiser:** if the position has any registered `eql` values, the argument itself when it is `eqv?` to one of them (a small scan or hash, by the length of the set), and its class key otherwise. The set is on the generic, since adding an `eql` method changes it;
   - **predicate specialiser:** a registered predicate's result cannot be known from the class, so the key is the class if the predicate is declared stable for the class (the library asserts it) and *uncacheable* otherwise, which sends every call to the discriminator. Julia's value-based `Val` dispatch and Dylan's limited types are class-keyed. Truly dynamic predicates stay slow on purpose and visibly so.

   The cache maps the tuple of keys to an **effective method**, a procedure the discriminator returned. A site holds up to four entries, each a tuple of at most four keys and a method; a miss goes to the generic's own cache, a hashed table on the tuple (a linear scan is better than a hash for the few entries most generics have, as GOOPS found, so it switches by size); a miss there calls the discriminator, which returns the effective method and which positions' keys it consulted, and the VM installs the entry. Keys that no `eql` or predicate specialiser consulted at a position are widened to the class key's identity, so one entry covers every value of the class. Class identities are small sequential integers hashed by a multiply, not random numbers as GOOPS's per-class hash sets and PCL's wrappers use: expansion is deterministic (ADR 0001 #4) and a run should be too.
10. **The discriminator is where CLOS lives, and the full MOP with it.** The MOP is Scheme, in a library; the substrate gives it five things so that it stays fast:
    - **The discriminator is the generic's own computed function, and the substrate caches what it returns.** The generic's hidden fields hold it, as AMOP's `compute-discriminating-function` installs one per generic. On a miss the VM calls it with the argument tuple and it returns an effective method and the argument positions whose classes or `eql` values it consulted; the VM installs the entry (item 9). For the standard generic-function class the library's discriminator calls `compute-applicable-methods-using-classes`, which AMOP defines to say whether its answer depends only on the classes (the *definitive* flag), then `compute-effective-method`. A definitive answer is cached by class keys; a non-definitive one (a custom `compute-applicable-methods`, a predicate specialiser) is run against the actual arguments and returned uncached, or cached on the positions the library names. A user metaclass or method on any of those protocol generics changes what the discriminator does and nothing else, so a MOP user pays only on misses.
    - **A generic can opt out of the cache.** One whose library installs a discriminating function that does the whole call itself (an AMOP discriminating function in the full sense) is marked `custom`; calling it is an ordinary applicable-object call (item 15), and the substrate caches nothing for it.
    - **Slot access goes through shapes, with MOP hooks only on non-standard slot classes.** `finalize-inheritance` computes the class precedence list and the slot layout and makes the root shape; a slot whose slot-definition object is of a standard class is a plain named property, read by `slot-ref` or `get` at shape speed. A slot whose slot-definition class is non-standard (lazy, persistent, computed) is a `hooked` property whose hook is `slot-value-using-class`, `(setf slot-value-using-class)` and their relatives (item 7), cached only as the resolution (item 8).
    - **A way to register a library-level dependency.** Optimised paths a MOP library builds for itself, such as a `make-instance` that skips the `initialize-instance` and `allocate-instance` generics while no user method exists on them for the class, are valid under conditions; the library creates a validity cell for each (item 8), and adding a method or redefining a class clears it. This is the same eager-dependents mechanism as the VM's own (item 12), exposed as a primitive, so the library does not need a mechanism of its own.
    - **Metaobjects are objects.** Classes, slot definitions, generics and methods are instances with shapes, and the metacircular start-up (`standard-class` is an instance of itself) uses the class value's one late set (item 1).

    Python's binary-operator protocol, a Julia-like method table and Dylan's `define method` are different discriminators over the same cache.
11. **Caches live in run format only, in per-function site tables (provisionally).** Conversion allocates a **site** for each `get`, `set!`, `has?`, `add!` and `slot-ref` that is given a shape variable, and for each `dispatch`, and the site is in the converted function's own table. The leaning is per function, because functions are converted lazily (#55) and a table owned by its function is created, used and freed with it, where a per-module table (the one ADR 0005 #5 gives `dispatch`) would have to be sized for sites whose functions are never converted. Slice 1 decides it by measurement (below). The distribution IR names no site and no cache, so it stays the same size and is validated the same way. A site is empty until its first execution. The runtime fills it only after the checked slow path has run and has established the fact: no code, cached or written by an artifact, can make a site say something the VM did not find out. **Sizes (first guesses for the benchmark):** a table entry is one word, 0 when empty, pointing at a block allocated on first use; a monomorphic block is about six words (receiver shape, resolution or index, holder object, holder shape, validity cell, flags, with the call-site scope reserved: item 15), plus a two-word list node for each dependency it is on (below); on the second shape it grows to a polymorphic block of up to four entries; past that the site is megamorphic and uses a per-isolate cache of fixed size keyed by `(shape, key)`, direct-mapped, as V8's stub cache is. Blocks are charged to the isolate's memory limit and freed with their function. The megamorphic cache holds resolutions too, so holders and validity cells, but it belongs to no module, so its references act as roots: a holder (a prototype, say) stays alive until its entry is evicted or invalidated. The cache has a fixed number of entries, so what it keeps alive is bounded, and a transient module's objects outlive the module by at most that much. **Lifetime and the collector.** A module's site tables are reported to the strategy as *children of the module's heap object* (for a transient module, the `Code` object that every closure of its functions holds, ADR 0005 as built), so that the entries' references (effective methods, holders, validity cells) are ordinary counted edges and trial deletion sees them. A method closure refers to its module, the module to its tables, the table to the method: without those edges the cycle would leak, and without them a transient module (`eval`, `load_transient`) could not be freed with caching on. Entries are cleared by invalidation (below), and a counted store. When a function's table is freed (a transient module going away, or lazy conversion #55 dropping a function's converted code), each of its blocks **unlinks itself from the dependents lists it is on**: the lists are intrusive, so an unlink is constant time and needs no walk of the list. The alternative, lists that hold their sites weakly, would need weak references (#37), which slice 1 does not have, and would leave dead entries for an invalidation to sweep over. **The sizes are limits:** the polymorphic limit, the dispatch arity, the megamorphic cache's entries and `max_shapes` and `max_shape_properties` become fields of ADR 0023's configuration type, so an embedder bounds the memory a hostile program can spend on caches and shapes.

    **Slice 1's benchmark plan.** Build both placements behind one switch and measure, on the same machine, best of five, with the memory strategies that matter (no collection and one of each counting kind): (1) *placement*, per-function tables against per-module tables; (2) the *polymorphic limit* at 1, 2, 4 and 8; (3) the *megamorphic cache* at 0 (full lookup), 128, 512 and 2048 entries; (4) the *dispatch arity* held inline at 2 and 4 keys. Workloads: a monomorphic field-read loop over records and open objects; sites that see 2, 4 and 8 shapes in rotation; a megamorphic site over 16 and 64 shapes; an ES-style prototype method call through the miss hook; a generic with 1, 2 and 4 methods, with and without an `eql` specialiser; and a load test with a module of ten thousand sites, of which a tenth run. Recorded for each: time per access, instructions per hit, bytes per site, time to convert, and the hit rate. Per-function tables are kept unless per-module tables win steady-state time by more than noise (5%) or lose on neither memory nor conversion time. The limits are set from the knee of each curve, not from the first guesses.
12. **Invalidation is by eager dependents, with no world age.** What can go stale: a class's slot layout or precedence list (CLOS redefinition), a generic's methods or `eql` sets, a prototype chain (a validity cell), a class's hook, a shape that a cache names. Shapes themselves are immutable, and a layout change makes a new shape, so a cached `(shape, index)` is right for as long as the shape exists.

    - **Eager dependents.** Each generic, class, validity cell and shape keeps a list of the sites that depend on it, as HotSpot records the dependencies of compiled code and ADR 0017 #12 already provides. Changing one clears those entries, writing to the function's table and never to code (ADR 0005 #10). Cost: a list per generic, class and shape, updated when an entry is installed. Benefit: a hit does no check beyond its guard and, for resolutions that need it, a cell compare. A Julia-style world counter (a global number bumped by every method or binding change, with each task seeing the world it started in) is not used. Julia needs it because compiled code inlines across methods and tasks run in older worlds ([Julia manual](https://docs.julialang.org/en/v1/manual/worldage/); [Belyakova et al., OOPSLA 2020](https://dl.acm.org/doi/10.1145/3428275)); an isolate's tasks are never parallel, and a cache that an invalidation clears needs no counter to compare.
    - Obsolete instances (the other half of class redefinition): redefinition makes a new root for the new layout and marks the old shapes **obsolete**, a flag on the shape. An access that meets an obsolete shape takes the slow path, which calls the class's update protocol (`update-instance-for-redefined-class` in CLOS), builds the new slots, and calls `become-shape`. This is PCL's wrapper invalidation: instances are migrated on next use, never walked eagerly, and a hit costs nothing extra because an obsolete shape is simply never in a cache. V8 deprecates maps and migrates their objects in the same way.

    **Continuations and running frames.** A cache holds the answer to a lookup, and a frame that already made the call holds its own copy of the result. Re-entering a captured continuation resumes in the frames as they were and does not repeat any dispatch, so a continuation captured before a method was added continues with the method it had chosen, as a call that had already begun would. **A guarded access always re-checks its guard:** a slot read compares the shape, a dispatch hit compares the key tuple, a resolution compares its validity cell. A stale entry therefore misses and takes the slow path; no retry protocol exists, and nothing depends on an invalidation having run before a task switch. The one write that can go stale is installing a dispatch entry: a discriminator that yields (it awaits the host) may return after another task has added a method, so an entry is installed only if the generic's method-set stamp, read when the discriminator started, is unchanged, and otherwise the call proceeds with the result uncached once. The stamp is read on installs, never on hits. The effective method is an ordinary closure, kept alive by whoever holds it. Code a JIT specialised on a cache's answer is the one case that needs ADR 0017 #12's rule: its dependency is recorded, invalidating it puts the entry back to the library's own code, and the old code stays alive while a frame or continuation refers to it.
13. **Safety and validation.** No artifact has to be trusted to be correct about objects:
    - Every object operation is checked as it runs: that the operand is an object, that a shape matches or that a lookup found the key, that a slot index is below the shape's slot count, that an element index is below the store's length, that `become-shape` stays within capacity. A guarded access reads at most the object's own capacity.
    - The validator needs to know nothing about shapes or classes. Shapes are values; the object operations are primitives like `car` and `vector-ref`, with effect sets, and are validated as such. There is no new rule to enforce and none for a fuzzer to find wrong.
    - Caches are never in the distribution format and are filled only by the runtime from facts it has established (item 11). A hostile artifact can only make a site megamorphic, which costs speed.
    - Resource use is bounded by existing limits plus two: `max_shapes` (which makes `shape-root` raise a catchable error) and `max_shape_properties`, and property keys count against the symbol cap of ADR 0023 when they are interned symbols, which data-derived keys are not (item 14). Slow paths, hooks and discriminators run as Scheme code under the fuel budget, so a hostile hook cannot stall the host.
    - Capabilities (ADR 0009) are unaffected: an object is data. Reaching a Rust object through a bridge (ADR 0016) goes through the bridge's own checks; a bridged type can present itself as a class whose hooks are Rust procedures.
14. **Property keys: symbols on the fast path, any `eqv?`-comparable key beside them.** A shape's properties are named by symbols, which compare with `eq?`, and that is the whole fast path. An object may also have a key that is any other `eqv?`-comparable value (a fixnum that is not an element index, a character, an uninterned symbol is already a symbol): the first such `add!` moves the object to dictionary mode (item 3), whose table compares keys with `eqv?`, and, for strings only, by contents. A `get` with a non-symbol key on an object in shape mode finds nothing in the shape and goes to the hook. ES semantics see one key per string, because the runtime interns literals and existing symbols as just described, so ES objects with ordinary property names stay on the fast path; an ES `Symbol` is an uninterned symbol (an unforgeable identity), and an ES `#private` name is an uninterned symbol made per class evaluation, so no other code can name it and no scope check is needed. Integer-like keys are elements (item 6). The ES runtime interns a key only when it is a *literal* in the source, or a computed string that is *already* an interned symbol (a lookup that never makes a new symbol). Any other computed string key stays a string, and putting it on an object puts the object in dictionary mode, so keys derived from data (a JSON object's, a request's) cannot grow the symbol table, which is not collected yet (#46) and is capped by ADR 0023 in the meantime. A dictionary table **copies a string key on insert** (or freezes it, as ADR 0002's *immutable* flag does), since Scheme strings are mutable and a key that changed under the table would be lost.

### Applicable objects, sealing and link-time resolution

15. **Applicable objects and scope.**
    - **A class flag makes its instances callable.** A root whose class value is marked `applicable` has instances that `call` accepts: the VM calls the class's **apply hook** with the object and the arguments. This is CLOS's funcallable-standard-object, an ES callable object, a Python object with `__call__`, and a generic function (an applicable object whose hook runs `dispatch`). It is cached like dispatch: a site that calls an object caches `shape → apply hook` (a resolution, item 8), so an applicable-object call costs a shape check and a call. ADR 0002 #3's applicable records are the same rule.
    - **Call-site scope is designed in and built later.** A site block and a dispatch key tuple each reserve a word for a *scope*, compared by `eq?` and zero when absent, so a lookup that depends on where the call is (Ruby refinements) can be added by a later slice without changing a site's layout. `get-in` and scoped `dispatch` are listed in the operation table (item 7) and are not built in the first slices.

16. **Sealing and link-time resolution of `dispatch`.** ADR 0017 #11 lets the linker resolve a `dispatch` site to a direct call when "the generic function's rules guarantee no later method can change the answer", and leaves the rule open (its Left open). Here it is. Two separate things are declared, because they answer separate questions: *sealing* says who may add to the set of classes and methods, and *stability* says the answer depends only on that set.
    - **A sealed class** has a closed set of direct subclasses: the subclasses declared in its own library. Sealing forbids subclassing from any other library, redefinition in place (a changed slot list, precedence list or metaclass), and `change-class` to or from it. It is a flag on the root and is in the library's interface, so the linker reads it without running code. A class with no subclasses at all is a *leaf*, the strongest case.
    - **A sealed generic** may only be extended under the **orphan rule: a library may add a method to a generic only if it defines the generic or defines a class that appears in the method's specialisers.** An `eql` specialiser counts as naming the class of its value, so only the generic's own library, or the value's, may add one. Sealing forbids every other library's method, forbids removing a method, and forbids redefining the generic. An unsealed generic is unconstrained; Dylan's sealed generics are the model (a sealed domain), simplified to whole generics. The rule is enforced when a `define-method` loads, which raises, and the declaration and the library's hash are in the interface.
    - **Why the rule gives a closed world without whole-program loading.** A call's argument classes are known classes. Every library that can add an applicable method owns the generic or one of the method's specialiser classes, and a specialiser class is a superclass of an argument class (or the class itself), so its library is already in the argument class's import closure. The linker therefore sees every method that can apply, from libraries already loaded, and a library loaded later cannot add one. This is what lets a program load libraries dynamically (ADR 0009) without invalidating a resolution, until one of those libraries is replaced (below).
    - **Stability.** A generic is *stable* when its discriminator is a pure function of the argument classes and the method set: the standard generic-function class with standard method combination, no predicate specialisers, and no user method on the MOP protocol generics for it (items 10 and 18). A generic with a user metaclass that changes dispatch is not stable unless the metaclass declares it, so for it link-time resolution is **off** and the caches are the only path. Sealing is still enforced for it, since sealing is about who may add, not about how dispatch is computed. Making an unstable sealed generic an error was considered and rejected: it would punish a MOP user for a declaration that costs nothing but the optimisation.
    - **What resolution produces.** For `dispatch g(args…)` with `g` sealed and stable, the linker asks the generic's own discriminator for each class tuple (it is Scheme code and runs at link time) and emits: **a direct call with no guard** when each argument's class is proven (a leaf class, or a value just made by its constructor); **a class switch with a direct call in each branch, and the original dispatch site as the fall-back** when each argument's static class is sealed with at most four leaf subclasses (union splitting, as Julia does for small unions); and otherwise **the dispatch site unchanged, with its inline cache seeded** with the entries the linker computed. The effective method is a closure, so a direct call to it is a `call direct`. Proving a class needs type facts, which come from the typed IR (#33) or from local inference over constructors; without them only the third form applies, which is still correct.
    - **Dependencies.** A resolved site records the hashes of the libraries it relied on: the generic's, and the owners of the classes in its tuples (ADR 0017 #11, #12). A cache entry under those hashes is correct until one of them changes.
    - **Hot module replacement.** Reloading a library that sealed something invalidates what was resolved against it, through the same dependents lists (item 12): each such site goes back to its library's own code or dispatch, and is relinked in the background. Sealing forbids in-place redefinition, so a sealed class is *replaced* by the new version's class (a new root), not changed; instances of the old class keep the old shape and old methods, and are migrated or not as the HMR record says (Left open). A resolution made against the old class stays correct for old instances.
    - **Options.** *Seal whole generics only, with no extension by others:* simplest and fully closed, but a library cannot give its own class a `print-object` method on a standard generic, which kills the main use of generic functions across libraries. *Whole-generic sealing with the orphan rule (recommended):* closes the world as argued and keeps extension. *Dylan's sealed domains,* sealing a generic only over a set of specialiser tuples, so one generic can be open for some classes and closed for others: finer, and the natural refinement, but a generic function's every extension then needs a domain check, and nothing in the first uses needs it. Left open as a refinement of the recommended rule.


### Records, libraries and the plan

17. **Records become fixed shapes, in the first slice.** `define-record-type` makes a root shape (class = the record type descriptor, `fixed` set), the constructor is `alloc-object`, an accessor is `slot-ref` with the shape closed over, and a predicate is `eq?` of `shape-of` against the type's shape. The layout is unchanged, so a record costs what it costs now, and a field access is the compare it is now. What follows is one mechanism: the debugger's inspector, `equal?`, printing, bridges and the JIT see one object kind with a shape, not records beside objects. R7RS has no record inheritance, so the predicate is exact; R6RS's `parent` would test the class chain, which lives on the class value. The change touches the VM, conversion, the debugger and the bridges at once, and goes in behind the existing record tests, as the first user of the substrate, so there is never a second object kind.
18. **CLOS, with the full MOP, and ES6 are libraries, not VM features.**
    - **CLOS and its MOP** in Scheme, in `vali/` or a package of their own: `define-class` is `ensure-class` and `finalize-inheritance`, which compute a class precedence list and slot layout and make a root shape per class; `make-instance` and `allocate-instance` are `alloc-object`; `slot-value` and accessor generics are `get` or `slot-ref` with a site, or `slot-value-using-class` for non-standard slot classes; `define-generic` and `define-method` build the generic object, its methods and its tables; method combination, `compute-applicable-methods`, `compute-effective-method`, `call-next-method` and `no-applicable-method` are generic functions in the library; class redefinition is the obsolete-shape protocol of item 12. The standard classes of the built-in types (`<integer>`, `<pair>`, `<string>`, …) and `eql` specialisers fall out of items 9 and 10. With the class-keyed cache, accessors on a known class compile to a guarded slot read: SBCL's PCL does the same, and stores the slot offset directly in the memoisation table when a generic is used as an accessor. The library is built in the order the slices allow (item 19): the standard object system first, the metaobject protocol's replaceable parts after, with the same VM support.
    - **ES6** as an ES runtime library: objects with `[[Prototype]]` are shapes rooted at the prototype (item 2), property descriptors are flags, accessor properties are `hooked`, `Symbol` and `#private` are uninterned keys and string keys are interned (item 14), arrays are open objects with elements, prototype lookup is the miss hook with validity cells (item 8), callable objects are applicable (item 15), and `Proxy` is an `exotic` root. The runtime also needs a UTF-16 string type, double and int32 number semantics, Promises on tasks and continuations (ADR 0004, 0008), `WeakMap` (#37), `RegExp` (#36) and `eval`. Each is a primitive set or a record of its own; this one provides none of them.
19. **Plan, in slices each testable alone.** (a) **shapes, `alloc-object`, `slot-ref`/`slot-set!` and records as fixed shapes**, with immortal shapes behind the final API (counted shape word, stuck counts), and the **cache benchmark of item 11** on a first `get`/`set!` site, which sets the placement and sizes before more is built on them; (b) `get`/`set!`/`has?`/`add!`/`delete!` with sites, the miss hook, `hooked` properties and dictionary mode, with a Scheme prototype-object test library; (c) elements; (d) `dispatch`, generic and applicable objects, the dispatch cache and the discriminator, with a standard-CLOS test library; (e) **sealing**: the class and generic flags, the orphan rule at `define-method`, interface entries, and the linker's resolution (a link-time slice, with ADR 0017 #11); (f) **collectable shapes**, together with weak references and ephemerons (#37): the weak transition edges, the dependents-list clearing on free, cycle collection of class and shape, and the check that an old class's shapes are reclaimed once its instances are gone, before hot module replacement is built; (g) scoped `get-in` and `dispatch`, when a front end needs them; (h) the full CLOS library with the MOP's replaceable parts, and the ES runtime library, outside this record. Each slice is measured on benchmarks (`benchmarks/`) before the next, with an ES-style property benchmark and a CLOS-style generic call benchmark added in (b) and (d).

## Consequences

- **Records, CLOS instances, ES objects and bridged Rust objects are one kind of object.** The debugger, printer, `equal?`, bridges and JIT see a shape and slots. The record type code and its descriptor word merge into the object's.
- **The IR grows by one named set of primitives and by ADR 0017 #5's `dispatch`, defined.** No other IR construct changes, and the validator gains no rule (item 13).
- **The run format gains sites and the three cache shapes.** They are in per-function tables (item 11) and are never rewritten code (ADR 0005 #10). They are built at conversion, filled by the runtime, and cleared on invalidation; they are not cached to disk with the module's run-format code (a cached copy has all-empty tables).
- **Under the memory strategies,** a shape is a heap object (item 1) whose count changes once per allocation and per transition and never on a read, so object access is as cheap as a record's now. Until collectable shapes land, a shape's count is stuck, as a constant's is (ADR 0020), and nothing is freed. Objects describe their pointers by type (ADR 0003): the shape word is a counted reference, `props` and `elements` are counted children, and inline slots are counted from the header's slot count; objects are candidates for trial deletion like records and closures, and so are a class and its root shape, which refer to each other. Slot stores go through the store hook like `vector-set!`. The side-counted pair layout is untouched, because objects are not pairs. Under no collection shapes are never freed. A tracing or moving strategy later traces the shape word like any pointer and moves shapes with the rest of the heap; the identity of a shape is its address then, and a site that caches it is cleared when it moves, as it is when it is freed. Cache entries holding effective methods, holders and validity cells are heap references from site tables that are reported as children of their module's heap object (item 11), so they are counted or traced like any other edge, trial deletion sees the cycles through them, and clearing an entry is a counted store.
- **Tier-up and the JIT.** A closure's function entry is still all tier-up replaces (ADR 0002). The JIT reads a site's current block as a hint, emits a shape compare and a slot load (shapes are immutable, so the compare needs no assumption), and registers dependencies only for validity cells and shapes it relied on. It does not speculate, and a miss is the slow path, not a deoptimisation.
- **Per-object memory:** a fixed object is header, shape and fields: what a record costs now. An open object adds `props` and `elements`, four words in all before slots. A shape is a few tens of bytes, plus its transitions and the list of sites that cache it; a site is one word empty.
- **Hostile code can fill the shape table** (bounded by `max_shapes`: `shape-root` then raises a catchable limit error and `shape-extend` moves objects to dictionary mode; collectable shapes also let it be reclaimed) and the symbol table (bounded by ADR 0023's cap), and can make caches megamorphic. Cache and shape sizes are fields of ADR 0023's limits. It cannot read or write outside an object or forge a cache entry.
- **A bad hook is slow or stale, and unsafe by no construction of its own.** It runs under fuel. A hook that returns a wrong resolution, or a library that fails to clear a validity cell, can give a stale answer, and cannot read outside an object: a `slot-of` hit compares the holder's shape on every hit, and the index was checked against that shape when the entry was filled (item 8).
- **ADR 0017 #11's link-time resolution of `dispatch` has its rule (item 16).** Sealed classes, sealed generics under the orphan rule and stable discriminators give the linker a closed world without loading the whole program, and a reloaded library invalidates exactly what was resolved against it. Closing ADR 0017's open rule (its Left open) is an edit to that record when this one is accepted. `vali build` (ADR 0017 #15) can resolve every site the types allow, and the caches are the common path in between.

## Questions to settle before accepting

- **Sealing granularity** (item 16): whole-generic sealing under the orphan rule as recommended, or Dylan's sealed domains. And the bound on a class switch's branches (four leaf subclasses is a first guess), which the benchmark of slice (e) can set.
- **The sizes** of item 11: placement, polymorphic limit, dispatch arity and megamorphic cache size are set by slice 1's benchmark, and `max_shapes` and `max_shape_properties` (first guesses 65,536 and 128) by ADR 0023's review of limits.
- **Whether a root's class value may be set once after creation** (item 1), which the MOP's start-up needs, or the library bootstraps with a placeholder class that it replaces by `become-shape` on each object.
- **Whether the `Record` type code survives** as an alias for a fixed object, or goes.
- **Whether `become-shape` on collectable shapes** needs a write barrier under a future tracing strategy, or only the counted store.


## Out of scope

Recorded so they are not mistaken for omissions:

- **Value types, unboxed fields and interior pointers.** Truffle's typed locations, struct fields stored inline, arrays of structs. They need the planned typed IR (#33).
- **Static vtables and link-time layout.** A class fixing its fields and method slots (JVM, Kotlin). Possible later through link-time resolution (ADR 0017 #11, #15).
- **Algebraic data types with a tag switch.** A variant type's `case` is a different dispatch, on a tag and not a class, and wants a different instruction (a jump table), not this cache.
- **Laziness and thunks,** as a language feature (Haskell). Promises, ES-style, are a library over tasks and continuations.
- **Actor processes** (Erlang). Isolates and tasks are ADR 0008's concern.
- **Shared-memory threads** and a memory model. ADR 0008's single-threaded isolates are a deliberate choice; none of this design needs atomics or locks on shapes, caches or objects, and adding threads would reopen all three. Truffle's model has a thread-safe variant ([Daloze et al., OOPSLA 2016](https://stefan-marr.de/downloads/oopsla16-daloze-et-al-efficient-and-thread-safe-objects-for-dynamically-typed-languages.pdf)); this record does not adopt it.
- **Smalltalk `become:`,** which swaps two objects' identities. `become-shape` changes one object's layout, not its identity; a general `become:` needs a forwarding pointer in every object and read barrier, which ADR 0003's strategies do not give.
- **The non-object needs of ES6** (UTF-16 strings, double and int32 number semantics, Promises and async functions, `WeakMap` and ephemerons, `RegExp`, `eval`, Proxy beyond the `exotic` flag): primitive sets and records of their own.

## Left open

- **Hot module replacement** needs a record of its own: module versions, invalidating dependents (items 12 and 16 give the mechanism), migrating state, keeping old code alive while continuations refer to it (ADR 0017 #12), and instances of old classes outliving their module (item 16 says a sealed class is replaced, not redefined). Collectable shapes (item 1) are here because of it; the record must not be accepted before they land.
- **Sealed domains** as a refinement of item 16.
- **Typed fields and unboxed element kinds** (flonum arrays), once the typed IR exists (Out of scope).
