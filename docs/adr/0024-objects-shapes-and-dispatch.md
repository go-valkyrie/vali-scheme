# 0024. Objects, shapes and dispatch

- **Status:** Proposed
- **Date:** 2026-11-19
- **Related:** 0002 (values, headers, records, tier-up entries), 0003 (memory strategies), 0004 (continuations), 0005 (run-format bytecode, per-module tables), 0008 (isolates, one thread at a time), 0009 (capabilities), 0012 (distribution format, the validator), 0016 (Rust objects), 0017 (the IR; #5 `dispatch`, #11 link-time resolution, #12 invalidation), 0020 (constants), 0023 (resource limits)

## Context

Vali's only user-defined data type is the record: a header, a type descriptor and a fixed list of fields, read and written by `%record-ref` and `%record-set!` after a check against the descriptor (`crates/vali-runtime/src/records.rs`; `define-record-type` in `(scheme base)`). ADR 0017 #5 names a generic `dispatch g(…)` instruction and #11 lets the linker resolve it, but neither says what a generic function is, what it dispatches on, or what an object is beyond a record.

The owner wants three things from this, in this order:

1. **CLOS as an option:** classes, generic functions with multiple dispatch, `eql` specialisers, method combination, and class redefinition, with or without the full metaobject protocol.
2. **ES6 objects as a bonus:** prototypes, property descriptors, `Symbol` keys, arrays with holes, `#private` names, and optionally `Proxy`.
3. **The door open for other front ends** (Python, Ruby, Lua, Smalltalk-likes, Dylan, Julia-like DSLs) that an embedder might compile to Vali's IR to get its sandbox, limits and validation (ADRs 0009, 0012, 0023). Their object models differ, but the VM needs the same few mechanisms under each.

A bytecode VM with no object support cannot make any of these fast, and cannot make them safe without checks that cost what the fast path saves. Every fast dynamic-language VM converged on the same substrate, and the substrate is small enough to be language-neutral:

- **Shapes** (V8's maps, Self's maps, PyPy's maps, Truffle's shapes): an immutable description of an object's layout, shared by every object built the same way, so that "which slot holds `x`" is a property of a pointer comparison. V8 puts the shape in the first word of every object and describes properties in a descriptor array shared along a transition chain; objects with the same properties added in the same order end up with the same map ([V8, hidden classes](https://v8.dev/docs/hidden-classes)). PyPy's maps are "immutable, immortal and reused as much as possible"; an instance is a map pointer plus a storage array, and a million three-field instances took about 40 MiB with maps against 177 MiB without them (32-bit, [PyPy, 2010](https://pypy.org/posts/2010/11/efficiently-implementing-python-objects-3838329944323946932.html)). Truffle's object model is the same idea with typed storage locations: a shape maps property names to locations in a fixed number of in-object fields plus an extension array ([Wöß et al., PPPJ 2014](https://chrisseaton.com/rubytruffle/pppj14-om/pppj14-om.pdf); [Truffle's Dynamic Object Model](https://www.graalvm.org/dev/graalvm-as-a-platform/language-implementation-framework/DynamicObjectModel/)).
- **Inline caches** at access and call sites, which remember the shapes seen there and what they resolved to. V8 keeps up to about four maps at a site (polymorphic) and falls back to a global stub cache keyed by map and name once a site goes megamorphic ([V8, hidden classes and ICs](https://chromium.googlesource.com/v8/v8/+/HEAD/docs/runtime/hidden-classes-and-ics.md)).
- **Dispatch caches** for generic functions. GOOPS memoises the method chosen per tuple of argument classes on the generic itself, with a short linear search for small caches and a hashed search for larger ones, and drops the cache when a method is added or a MOP method is redefined ([Wingo, 2008](https://wingolog.org/archives/2008/10/17/dispatch-strategies-in-dynamic-languages)). PCL, the CLOS implementation under SBCL, gives each class a *wrapper* with a stored value that generic functions' small memoisation tables are indexed by; redefining a class zeroes the wrapper's value, so instances of the old class miss the table on their next dispatch and normal dispatch pays nothing for the check ([Kiczales and Rodriguez, 1990](https://dl.acm.org/doi/10.1145/91556.91600); [summary](http://axisofeval.blogspot.com/2010/07/efficient-method-dispatch-in-pcl.html)). Julia keeps a method table per generic function, caches by argument types, and makes redefinition safe with a *world age*: a global counter bumped by every method or binding change, with each task seeing the world it started in ([Julia manual, world age](https://docs.julialang.org/en/v1/manual/worldage/)).

Constraints that come from Vali's other records:

- **The distribution format's validator is the security boundary** (ADR 0012 #9, 0017 #13). Distribution code holds only checked operations. Whatever objects add must be checkable without knowing any shape, and nothing a crafted artifact says may weaken memory safety.
- **Run-format bytecode is private and executes directly.** Loading fills in per-module tables but does not rewrite code (ADR 0005 #10). Dispatch sites already have a slot in a per-module table (ADR 0005 #5). This is where caches can live.
- **Nothing is speculative** (ADR 0017 #12, consequences). A cache that falls back to the full lookup on a miss is not speculation: there is no deoptimisation. A JIT that embeds a cache's answer must record what it relied on and be invalidated like any link-time decision.
- **One thread at a time uses an isolate's heap** (ADR 0008), and continuations copy frames (ADR 0004 #8). Both make several of the problems below easier than in a multi-threaded VM, and the second adds one that is easy to forget: a frame may resume after the world has changed.
- **Five memory-strategy variants are built** (ADR 0003): no collection, and deferred and precise counting, each with headered or side-counted pairs. An object design must be correct under all of them, and must not put a barrier or a count where one is not needed.
- **Limits apply to what hostile code can grow** (ADR 0023). A shape table and a property-key table are such things.

ES6's other requirements are not objects: UTF-16 string semantics, IEEE doubles with int32 truncation, Promises and async functions, `WeakMap` and `WeakRef` (ephemerons, #37), `RegExp` (#36), `eval` and Proxy. They belong to *primitive sets* and other records, as the notes on other front ends say. This one only has to leave them room: it keeps the object substrate free of anything that would stop an ES runtime from supplying them, and says where each meets it (below).

## Options

**A. A small language-neutral substrate in the VM and IR (recommended).** Shapes with transitions; allocation by shape; guarded slot and element access; `get`/`set` by key with inline caches that exist only in run format; `dispatch` over specialisers with a per-argument-tuple cache; a miss hook. CLOS and ES6 are libraries over it, and records become its simplest users. Costs: new primitive operations, a shape table and caches in the runtime, about as much new run-format surface as `dispatch` already needs, and a hook protocol that has to be right once. Buys: one mechanism for records, CLOS instances, ES objects and bridged Rust objects; fast paths that are a tag test, a shape compare and a load; invalidation in one place.

**B. Dispatch keyed on shapes only.** Single dispatch on the receiver's shape, as V8, Truffle and Smalltalk-style VMs do, and nothing else. Simpler cache (a site's entry is `shape → resolution`) and enough for ES and for Ruby or Python method calls. It fails the requirement that motivated the design: CLOS dispatches on all required arguments, with `eql` specialisers that depend on a *value*, and Python's binary-operator protocol tries one operand's method and then the other's (`a.__add__(b)`, then `b.__radd__(a)`), so the useful key is both classes. A library would rebuild multiple dispatch over a single-dispatch core, with its own caches in Scheme hash tables the VM cannot see, giving up the inline cache for exactly the calls that need it. Cheaper to start, more expensive to finish.

**C. No VM support: objects are records plus hash tables in Scheme.** An object is a record holding a class and a hash table (or alist) of slots; a generic function is a closure over a Scheme-side cache. GOOPS and Tiny CLOS are written this way, over a host with some VM help. Costs nothing in the VM and has no new safety surface, and `dispatch` stays unbuilt. But every property access is a hash lookup on a table the object carries: PyPy's figures above are the size of that cost for a dict-backed object, and a Scheme-level cache cannot be an inline cache, because only the VM knows when a site sees a shape. It would serve CLOS acceptably and every other language poorly, so the third goal would be abandoned in effect. Hash tables (#30) are needed for the dictionary fallback in A anyway.

**D. Adopt a Truffle-like object model wholesale.** Shapes plus typed storage locations (unboxed `long` and `double` locations, generalised to `Object` when a different type is stored, which changes the shape), property flags, extension arrays, and access nodes that cache per shape. The shapes, in-object slots plus an extension array, and per-site caching come over directly and are in A. The typed locations do not: they pay off when a partial evaluator can fold the shape check and the unboxed access across a whole call tree, and in Vali fixnums are already immediate (ADR 0002) and flonums boxed, so the gain is flonum fields, which belong to the planned typed IR (#33) and its unboxed fields. A copies Truffle's shape model and leaves its framework behind.

**E. Statically laid-out classes** (JVM and Kotlin style: a class fixes its fields and a vtable index per method, so a call is a load and an indirect call). Fastest for statically typed languages, but it needs the typed IR and the closed world that link-time resolution gives (ADR 0017 #11, #15). A can reach the same code when the linker proves a site monomorphic. Recorded as out of scope.

Two sub-choices inside A each have their own options, set out where they arise: what happens to an object with too many or too dynamic properties (transition tree against dictionary mode, item 3), and how caches stay correct when classes and methods change (eager dependents against a Julia-style world counter, item 12).

## Recommendation

Option A, built in slices (item 17), with these parts.

### Objects and shapes

1. **A shape is an immutable, isolate-lifetime description of a layout.** It is a first-class value of its own type code (`Shape`), made by checked primitives. It holds: the shape's *class value* (an opaque Scheme value, set at the root and inherited by every descendant); the properties in order, each a key, a slot index and a flags byte; the slot count; and its transitions, a small map from `(key, flags)` to the child shape. **Shapes live outside the heap, in a per-isolate table, and are never counted, traced or freed**, like interned symbols (ADR 0023 #1). A shape word in an object is therefore a plain pointer or table index, written once at allocation (and by `become-shape`, item 5), with no store hook under any strategy. A shape is identified by identity, so a shape check is one comparison. A shape table grows only by `shape-extend` and `shape-root`, so it is bounded by a new limit, `max_shapes`, in ADR 0023's configuration type; past it, objects go to dictionary mode (item 3).
2. **The class value is the root's identity.** Two objects have the same shape only if they share a root and the same properties added in the same order. The root's class value is what the other systems store in different places: PyPy puts the class at the end of the map chain, V8 puts the prototype in the map, PCL's wrapper points to the class. Here it is the CLOS class, the ES prototype, the Python type, the Ruby singleton or class, or a record type descriptor, and the VM interprets it only as an identity to key dispatch on, and as where the miss hook (item 7) lives. It is *the library's* choice what it means.
3. **Transition tree for ordinary growth, dictionary mode past a bound.** `shape-extend shape key flags` returns the child for that key, creating it on first use. A tree gives the sharing that makes caches work and costs one Rust-side node per distinct layout; it degrades when objects use many keys, delete keys other than the last added, or use keys chosen by data (a hash map used as an object), since every distinct path then makes new shapes. Past `max_shape_properties` (first guess 128), on a delete of anything but the last-added property, or when `max_shapes` is reached, an object switches to **dictionary mode**: its shape word becomes the *dictionary shape of its root* (one per root, shared, immortal, flagged `dict`), and its `props` word points to an open-addressed table in the heap holding key, flags and value. V8 uses the same two modes; PyPy moves an instance's data into a dictionary when a non-string key arrives, and judges the cost acceptable because it is rare ([PyPy, 2010](https://pypy.org/posts/2010/11/efficiently-implementing-python-objects-3838329944323946932.html)). Taking the table into the heap, and a shared shape for every dictionary object of one class, means a dictionary object adds no shape to the table and its properties die with it: the per-object property table a Rust-side "unique shape" would need could never be freed, which is the leak that would make this a denial-of-service lever. Inline caches never cache named lookups on a dictionary shape; they take the table lookup each time. Moving between modes is one-way.
4. **Layouts.** Two, chosen at allocation and recorded in the header's runtime data:
   - **Fixed:** header, shape, then the slots. A record with three fields is 40 bytes, exactly as now (the descriptor word becomes the shape word). The shape must have `fixed` set at its root, so `add` and `delete` raise. This is the layout records use.
   - **Open:** header, shape, `props`, `elements`, then a number of inline slots. `props` points to the heap vector that holds slots past the inline ones (or the dictionary table, in dictionary mode) or is empty; `elements` points to the element store (item 6) or is empty. Four words of fixed overhead, plus eight bytes a slot. The inline count comes from the allocation site's size hint, so an object does not start by moving its first properties out, which V8 solves with slack tracking and Truffle with `@DynamicField`s. An ES object with four properties is 64 bytes plus no extra allocation. Both layouts keep their slot count in the header's 24 bits of runtime data, as a record keeps its field count now (ADR 0002 #7), so the strategy can walk an object's pointers without the shape.
5. **Per-object behaviour is the object's own shape.** `become-shape o shape'` changes an object's shape word. It is checked: `shape'` must have a slot count no larger than the object's capacity (inline plus `props`), and new slots read as the unspecified value until written. This is the one operation that lets a library implement Ruby singleton classes (`def obj.m`, which move the object to a fresh root whose class is a singleton), ES `Object.setPrototypeOf` (move to the tree for the new prototype, re-adding the properties in order), CLOS `change-class` and class redefinition (below), and shape migration generally. Each new root costs one shape and its transitions, a few tens of bytes, which the library keeps cheap by making roots lazily and sharing them (an ES runtime caches "the root for objects whose prototype is `p`" on `p`). Because shapes are immortal this is a leak for programs that make a fresh root per object in a loop; the questions below ask whether shapes should become collectable.
6. **Elements: indexed storage beside named slots.** The `elements` word points to an element store whose header data holds a *kind*: **packed** (a vector, with a length and capacity), **holey** (the same, with a distinguished internal `hole` marker, ADR 0002's immediates) and **sparse** (an open-addressed table from fixnum index to value). Kinds only move one way, packed to holey to sparse, as V8's elements kinds do ([V8, elements kinds](https://v8.dev/blog/elements-kinds)); V8 also keeps unboxed SMI and double kinds, which are out of scope here (they need unboxed fields). An index far past the capacity moves the store to sparse instead of allocating. This gives ES arrays (holes, `length` as the store's length), Lua tables (the array part is elements, the hash part is props in dictionary mode), Python lists and Ruby arrays a representation, with the bounds check in the VM.

### IR operations and caches

7. **The operations are primitive operations in a named set, `(vali object)`,** with effect sets as in ADR 0017 #4. They are part of the IR's specification like any primitive, and a front end that does not use objects never mentions them.

   | Operation | Effects | What it does |
   |---|---|---|
   | `shape-root class flags`, `shape-extend shape key flags`, `shape-of o`, `shape-class shape`, `shape-slots shape` | `alloc`, `pure` | Make and read shapes. A key is a symbol (item 9) |
   | `alloc-object shape hint v…` | `alloc` | An object of that shape, with the given slots; fixed or open by the root's `fixed` flag |
   | `slot-ref o shape i`, `slot-set! o shape i v` | `read`, `write`, `may-raise` | **Guarded by shape.** Raises unless `o` is an object, `o`'s shape is `shape`, and `i < shape`'s slot count; a read-only slot refuses `slot-set!`. This is a record's accessor |
   | `get o key`, `get-in o key scope`, `set! o key v`, `has? o key`, `add! o key flags v`, `delete! o key` | `read`/`write`, `may-raise`, `may-capture` | Lookup by key. The slow path searches the shape (or the dictionary table), then runs the miss hook (item 8). Each is a cached site (below) |
   | `elt-ref o i`, `elt-set! o i v`, `elt-length o`, `elt-resize o n` | `read`/`write`, `may-raise` | Bounds-checked element access. A read past the end or at a hole returns the `hole` marker and lets the library decide (an ES prototype walk, a Python `IndexError`) |
   | `become-shape o shape` | `write`, `may-raise` | Item 5 |
   | `dispatch g(args…)` | every effect | Item 9 and 10; ADR 0017 #5 |

   Two property flags are interpreted by the VM: `readonly` (writes raise) and `hooked` (a read or write of this property calls the class's access hook with the object, key and value, which is how ES accessor properties and Python descriptors and `__getattr__` on a known name are expressed). All other flag bits belong to the library: ES's enumerable and configurable bits, for example. The VM never needs the meaning of a flag it does not interpret, so languages with other property attributes need no VM change.
8. **The miss hook.** When `get o key` finds neither a slot nor an element, or finds a `hooked` property, the VM calls the **hook of the shape's class value** with `(o key scope)`. A class value that is a record or object with a procedure in a known place supplies it; with none, `get` raises. This is `__getattr__`, `method_missing`, `doesNotUnderstand:`, an ES prototype-chain walk and a Proxy trap, all as one mechanism. A hook returns either a value or a **resolution**, which the site may cache: `(slot-of o' i)`, `(constant v)` or `(call f)`, plus a **validity cell** (a heap cell the library clears when what the answer depended on changes: a prototype's own properties, its prototype link). A hit on a cached resolution loads the cell and compares, as V8 does for prototype chains, and so skips the chain walk; a plain value return is not cached. **Misses are cached**: a site remembers `(shape, key) → absent, hook`, so the negative search is skipped even when the hook must run. This is what makes ES property reads that find the property on a prototype, and Ruby method calls that find the method on a superclass, as fast as a shape check and a cell check, instead of a search per level. Exotic objects (a Proxy) have a root flagged `exotic`: every operation goes to the hook and nothing is cached through it, so they cost nothing to anything else.
9. **Dispatch has a specialiser per argument position and a key per specialiser.** A generic function is an *applicable object* (the applicable flag of ADR 0002 #3, on its root): a record-like object with hidden fields for its dispatch arity `k`, the specialiser kinds used at each position, the cache and the **discriminator**, a Scheme procedure the library installs. `(g a b)` and `dispatch g(a, b)` run the same code. For each of the first `k` arguments the VM computes a *cache key*:
   - **class specialiser:** the argument's class value (a shape's root class for an object; a table of built-in classes for fixnums, pairs, strings, flonums and the other tagged values), which for an object is already on its shape;
   - **`eql` specialiser:** if the position has any registered `eql` values, the argument itself when it is `eqv?` to one of them (a small scan or hash, by the length of the set), and its class key otherwise. The set is on the generic, since adding an `eql` method changes it;
   - **predicate specialiser:** a registered predicate's result cannot be known from the class, so the key is the class if the predicate is declared stable for the class (the library asserts it) and *uncacheable* otherwise, which sends every call to the discriminator. Julia's value-based `Val` dispatch and Dylan's limited types are class-keyed. Truly dynamic predicates stay slow on purpose and visibly so.

   The cache maps the tuple of keys to an **effective method**, a procedure the discriminator returned. A site holds up to four entries, each a tuple of at most four keys and a method; a miss goes to the generic's own cache, a hashed table on the tuple (a linear scan is better than a hash for the few entries most generics have, as GOOPS found, so it switches by size); a miss there calls the discriminator, which returns the effective method and which positions' keys it consulted, and the VM installs the entry. Keys that no `eql` or predicate specialiser consulted at a position are widened to the class key's identity, so one entry covers every value of the class. Class identities are small sequential integers hashed by a multiply, not random numbers as GOOPS's per-class hash sets and PCL's wrappers use: expansion is deterministic (ADR 0001 #4) and a run should be too.
10. **The discriminator is where CLOS lives.** It receives the generic and the argument tuple and returns an effective method (and the consulted positions). A standard CLOS library implements `compute-applicable-methods`, ordering by class precedence list, standard method combination (primary, `:before`, `:after`, `:around`), `call-next-method` and `no-applicable-method`, in Scheme. A library that offers the MOP lets a user replace the discriminator per generic class, which is `compute-discriminating-function`; one that does not, ships one. The VM's share is only the cache and the keys. A Python-style binary operator, a Julia-like method table and a Dylan `define method` are different discriminators over the same cache.
11. **Caches live in run format only.** Conversion allocates a **site** for each `get`, `get-in`, `set!`, `has?`, `add!`, `slot-ref` that is given a shape variable, and `dispatch` in each module's table (the per-module table ADR 0005 #5 already gives `dispatch`). The distribution IR names no site and no cache, so it stays the same size and is validated the same way. A site is empty until its first execution. The runtime fills it only after the checked slow path has run and has established the fact: no code, cached or written by an artifact, can make a site say something the VM did not find out. **Sizes:** a table entry is one word, 0 when empty, pointing at a block allocated on first use; a monomorphic block is four words (shape, index or resolution, cell, flags); on the second shape it grows to a four-entry polymorphic block of twelve; on the fifth it becomes megamorphic, and the site uses a per-isolate cache of fixed size keyed by `(shape, key)` (first guess 512 entries, 24 KiB), direct-mapped, as V8's stub cache is. A module of ten thousand sites costs 80 KiB empty. Blocks are charged to the isolate's memory limit and freed with the module instance, like a module's constants (ADR 0020). Dispatch entries add the effective method, a heap value, so a site's entries are references from the module instance's table, which counts them like any heap-to-heap reference under the counting strategies; invalidation clears them (below).
12. **Invalidation is by dependents, not a global counter.** What can go stale: a class's slot layout or precedence list (CLOS redefinition), a generic's methods or `eql` sets, a prototype chain (a validity cell), a class's hook. Shapes cannot go stale, because they are immutable and a layout change makes a new shape, so a cached `(shape, index)` is right for as long as the shape exists.

    - **Eager (recommended).** Each generic, class and validity cell keeps a list of the caches that depend on it, as HotSpot records the dependencies of compiled code and ADR 0017 #12 already provides. Changing one clears those entries, writing to the module's table and never to code (ADR 0005 #10). Cost: a dependents list per generic and per class, updated when a cache entry is installed. Benefit: a hit does no extra check beyond the cell compare for resolutions that need it.
    - **Epoch.** Each generic and class carries a counter; an entry stores the counter value and a hit compares it. One load and one compare on every hit, but nothing to maintain. Julia's world age is the global version of this, which it needs because compiled code inlines across methods and tasks hold older worlds. The isolate's tasks here are never parallel, so a single world is enough.
    - Obsolete instances (the other half of class redefinition): redefinition makes a new root for the new layout and marks the old shapes **obsolete**, a flag on the shape. An access that meets an obsolete shape takes the slow path, which calls the class's update protocol (`update-instance-for-redefined-class` in CLOS), builds the new slots, and calls `become-shape`. This is PCL's wrapper invalidation: instances are migrated on next use, never walked eagerly, and a hit costs nothing extra because an obsolete shape is simply never in a cache. V8 deprecates maps and migrates their objects in the same way.

    **Continuations and running frames.** A cache holds the answer to a lookup, and a frame that already made the call holds its own copy of the result. Re-entering a captured continuation resumes in the frames as they were and does not repeat any dispatch, so a continuation captured before a method was added continues with the method it had chosen, as a call that had already begun would. The discriminator runs on the caller's task and may itself be interrupted by a method definition, an `eval`, or a task switch at an await; the VM installs its result only after checking that the epoch or dependents it read are unchanged, and otherwise retries once and goes uncached. The effective method is an ordinary closure, kept alive by whoever holds it. Code a JIT specialised on a cache's answer is the one case that needs ADR 0017 #12's rule: its dependency is recorded, invalidating it puts the entry back to the library's own code, and the old code stays alive while a frame or continuation refers to it.
13. **Safety and validation.** No artifact has to be trusted to be correct about objects:
    - Every object operation is checked as it runs: that the operand is an object, that a shape matches or that a lookup found the key, that a slot index is below the shape's slot count, that an element index is below the store's length, that `become-shape` stays within capacity. A guarded access reads at most the object's own capacity.
    - The validator needs to know nothing about shapes or classes. Shapes are values; the object operations are primitives like `car` and `vector-ref`, with effect sets, and are validated as such. There is no new rule to enforce and none for a fuzzer to find wrong.
    - Caches are never in the distribution format and are filled only by the runtime from facts it has established (item 11). A hostile artifact can only make a site megamorphic, which costs speed.
    - Resource use is bounded by existing limits plus two: `max_shapes` and `max_shape_properties`, and property keys count against the symbol cap of ADR 0023, since a key is an interned symbol. Slow paths, hooks and discriminators run as Scheme code under the fuel budget, so a hostile hook cannot stall the host.
    - Capabilities (ADR 0009) are unaffected: an object is data. Reaching a Rust object through a bridge (ADR 0016) goes through the bridge's own checks; a bridged type can present itself as a class whose hooks are Rust procedures.
14. **Property keys are symbols.** Keys compare with `eq?`, which is what shapes and caches need. An ES string key is interned to a symbol on its way in; an ES `Symbol` is an uninterned symbol (the same unforgeable identity), and an ES `#private` name is an uninterned symbol made per class evaluation, so no other code can name it and no scope check is needed for it. Integer-like keys are not named properties: they go to elements (item 6). Keys that arrive as data, such as a JSON object's, are interned and count against the symbol cap; past it, `get` and `set!` by key on a dictionary-mode object accept a string without interning, comparing contents, at a cost in speed. Whether to offer that is a question. Ruby refinements need a lookup that depends on *where the call is*, so `get-in` and a scoped `dispatch` take a `scope` operand, compared by `eq?` and part of the cache key; without one, the key is unchanged and the cost is nothing.

### Records, libraries and the plan

15. **Records become fixed shapes.** `define-record-type` makes a root shape (class = the record type descriptor, `fixed` set), the constructor is `alloc-object`, an accessor is `slot-ref` with the shape closed over, and a predicate is `eq?` of `shape-of` against the type's shape. The layout is unchanged, so a record costs what it costs now, and a field access is the compare it is now. What follows is one mechanism: the debugger's inspector, `equal?`, printing, bridges and the JIT see one object kind with a shape, not records beside objects. R7RS has no record inheritance, so the predicate is exact; R6RS's `parent` would test the class chain, which lives on the class value. Doing this *with* the first slice has a price: records are used by the whole runtime and standard libraries, and the change touches the VM, conversion, the debugger and the bridges at once; doing it *later* means two object kinds for as long as the delay lasts. Recommended: first slice, as the first user, behind the existing record tests.
16. **CLOS and ES6 are libraries, not VM features.**
    - **CLOS** in Scheme, in `vali/` or a package of its own: `define-class` computes a class precedence list and slot layout and makes a root shape per class (a shape tree per class; a slot is a named property in a fixed or open layout); `make-instance` is `alloc-object`; `slot-value` and accessor generics are `get` or `slot-ref` with a site; `define-generic` and `define-method` build the generic object and its tables; method combination and `call-next-method` are in the discriminator. Standard classes of the built-in types (`<integer>`, `<pair>`, `<string>`, …) and `eql` specialisers fall out of items 9 and 10. With the class-keyed cache, accessors on a known class compile to a guarded slot read: SBCL's PCL does the same, and stores the slot offset directly in the memoisation table when a generic is used as an accessor. How much of the MOP is public is a library question (below); the VM's share is the same either way.
    - **ES6** as an ES runtime library: objects with `[[Prototype]]` are shapes rooted at the prototype (item 2), property descriptors are flags, accessor properties are `hooked`, `Symbol` and `#private` are uninterned keys (item 14), arrays are open objects with elements, prototype lookup is the miss hook with validity cells (item 8), and `Proxy` is an `exotic` root. The runtime also needs a UTF-16 string type, double and int32 number semantics, Promises on tasks and continuations (ADR 0004, 0008), `WeakMap` (#37), `RegExp` (#36) and `eval`. Each is a primitive set or a record of its own; this one provides none of them.
17. **Plan, in slices each testable alone.** (a) shapes, `alloc-object`, `slot-ref`/`slot-set!` and records as fixed shapes (the memory-strategy and ABI work); (b) `get`/`set!`/`has?`/`add!`/`delete!` with sites, the miss hook and dictionary mode, with a Scheme prototype-object test library; (c) elements; (d) `dispatch`, generic objects, the cache and the discriminator, with a CLOS-subset test library; (e) the full libraries, outside this record. Each slice is measured on benchmarks (`benchmarks/`) before the next, with an ES-style property benchmark and a CLOS-style generic call benchmark added in (b) and (d).

## Consequences

- **Records, CLOS instances, ES objects and bridged Rust objects are one kind of object.** The debugger, printer, `equal?`, bridges and JIT see a shape and slots. The record type code and its descriptor word merge into the object's.
- **The IR grows by one named set of primitives and by ADR 0017 #5's `dispatch`, defined.** No other IR construct changes, and the validator gains no rule (item 13).
- **The run format gains sites and the three cache shapes.** They are in per-module tables and are never rewritten code (ADR 0005 #10). They are built at conversion, filled by the runtime, and cleared on invalidation; they are not cached to disk with the module's run-format code (a cached copy has all-empty tables).
- **Under the memory strategies,** shapes need no barrier, count or collection; the shape word is a plain store at allocation and at `become-shape`. Objects describe their pointers by type (ADR 0003): the shape word is skipped, `props` and `elements` are counted children, and inline slots are counted from the header's slot count; objects are candidates for trial deletion like records and closures. Slot stores go through the store hook like `vector-set!`. The side-counted pair layout is untouched, because objects are not pairs. Under no collection nothing changes. A tracing or moving strategy later finds shapes outside its heap and the shape word a non-pointer into the heap, so it needs no forwarding for them. Cache entries holding effective methods and validity cells are heap references that the module instance's table owns; the strategy counts or traces them as it does any other heap-to-heap reference (they are not constants, which ADR 0020 keeps outside the heap), and clearing a cache entry is a counted store.
- **Tier-up and the JIT.** A closure's function entry is still all tier-up replaces (ADR 0002). The JIT reads a site's current block as a hint, emits a shape compare and a slot load (shapes are immutable, so the compare needs no assumption), and registers dependencies only for validity cells and epochs it relied on. It does not speculate, and a miss is the slow path, not a deoptimisation.
- **Per-object memory:** a fixed object is header, shape and fields: what a record costs now. An open object adds `props` and `elements`, four words in all before slots. Shapes are a few tens of bytes each in the isolate's table; sites are one word empty.
- **Hostile code can fill the shape table** (bounded by `max_shapes`, after which objects use dictionary mode) and the symbol table (bounded by ADR 0023's cap), and can make caches megamorphic. It cannot read or write outside an object or forge a cache entry.
- **A bad hook is slow, not unsafe,** and under fuel. A hook that returns a wrong resolution is the library's bug, and bounded by the checks of item 13: a resolved `slot-of o' i` is re-checked against `o'`'s shape when filled.
- **ADR 0017 #11's link-time resolution of `dispatch` stays possible.** A sealed generic whose argument classes are known can be resolved to a direct call when the linker has the whole program, and `vali build` (ADR 0017 #15) can seal generics and resolve every site the types allow. The caches are the fallback and the common path in between.

## Questions to settle before accepting

- **How much of CLOS** the standard library offers: the standard object system with method combination and class redefinition only, or the full MOP (replaceable `compute-applicable-methods`, `compute-discriminating-function`, metaclasses). The VM supports either through item 10; what changes is the Scheme library's size, and whether users can rely on MOP behaviour.
- **Records as shapes now or later** (item 15), and whether the `Record` type code survives as an alias or goes.
- **Property-key kinds** (item 14): symbols only, with ES strings and Symbols mapped to them; or any `eqv?` value. And whether contents-compared string keys on dictionary-mode objects are offered, to keep data-chosen keys out of the symbol table.
- **Link-time resolution of `dispatch`** (ADR 0017 #11): left to the linker with caches as the fallback, or a language-level seal for generics so resolution is a property of the program and not of the link. ADR 0017's open rule (orphan or sealing) is where this lands.
- **Where caches live and how big:** per-module tables as proposed (item 11), or per function, which a JIT may prefer; the polymorphic limit (four), the dispatch arity limit (four keys inline), the megamorphic cache's size and whether it is configurable, and whether the sizes belong in ADR 0023's limits.
- **Shapes and the five memory-strategy variants.** Are immortal, capped shapes acceptable? Programs that create a root per object, in a loop, leak shapes up to the cap and then fall to dictionary mode. The remedy is shapes that can be collected: heap objects with weak transition edges, which needs weak references (ADR 0003's contract, #37) and costs a count or a trace per object's shape word and a barrier on `become-shape`. Does that wait for 0.0.1 or later?
- **Eager dependents or epochs** (item 12), or both: eager for generics, epochs for validity cells.
- **Invalidation across tasks.** Tasks of one isolate interleave only at yields, but a discriminator that awaits (it calls into the host) is a window in which another task can redefine a class. Is "retry once, then uncached" enough, or should dispatch tables take the isolate's world version to freeze a dispatch for its duration?
- **Hooked properties and caching:** whether a `hooked` property's result is ever cached (a getter may return anything), and so whether `hooked` calls are caches of "call this hook" only.
- **A scoped lookup's cost:** whether `get-in` and scoped `dispatch` belong in the first slice or arrive when a front end needs refinements.
- **Applicable objects:** whether any object can be made applicable by its root's flag (as records can now), or only generics and closures.

## Out of scope

Recorded so they are not mistaken for omissions:

- **Value types, unboxed fields and interior pointers.** Truffle's typed locations, struct fields stored inline, arrays of structs. They need the planned typed IR (#33).
- **Static vtables and link-time layout.** A class fixing its fields and method slots (JVM, Kotlin). Possible later through link-time resolution (ADR 0017 #11, #15).
- **Algebraic data types with a tag switch.** A variant type's `case` is a different dispatch, on a tag and not a class, and wants a different instruction (a jump table), not this cache.
- **Laziness and thunks,** as a language feature (Haskell). Promises, ES-style, are a library over tasks and continuations.
- **Actor processes** (Erlang). Isolates and tasks are ADR 0008's concern.
- **Shared-memory threads** and a memory model. ADR 0008's single-threaded isolates are a deliberate choice; none of this design needs atomics or locks on shapes, caches or objects, and adding threads would reopen all three. Truffle's model has a thread-safe variant ([Daloze et al., OOPSLA 2016](https://stefan-marr.de/downloads/oopsla16-daloze-et-al-efficient-and-thread-safe-objects-for-dynamically-typed-languages.pdf)); this record does not adopt it.
- **Smalltalk `become:`,** which swaps two objects' identities. `become-shape` changes one object's layout, not its identity; a general `become:` needs a forwarding pointer in every object and read barrier, which ADR 0003's strategies do not give.
- **The non-object needs of ES6** (UTF-16 strings, double and int32 number semantics, Promises and async functions, `WeakMap` and ephemerons, `RegExp`, `eval`, Proxy beyond the `exotic` flag): primitive sets and records of their own.
